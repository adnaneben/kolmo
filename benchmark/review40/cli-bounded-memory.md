# Bounded CLI memory: levels 4-9 through the file path, `-t` and `-dc` without the output (review40 #8, #104)

Branch `claude/cli-bounded-memory` against `main` 896dc6d6. Execution only: every compressed frame below has the same
SHA-256 on both binaries (column "same SHA-256"; for `-t` there is no output, for `-dc` the decoded stream is hashed).

## Method

- Machine: Apple M5 (4 performance + 6 efficiency cores, 10 threads), macOS, shared with other sessions' runs.
  **The load average was 10-170 during the night**, so wall times carry that noise. Every configuration ran main and
  the branch back to back (main, branch, in the same minute), each under `tools/timed.sh` and a gate that waits up to a
  minute for the load to fall below 10; the load at the start of each run is in the last column. Compare the pairs,
  not rows with each other. CPU time (user + system) is less sensitive to the load than wall time.
- Inputs: `silesia.tar` (211,947,520 B), `enwik8` (100,000,000 B), and `mix2g.tar` (2,246,307,840 B: a tar of the
  review corpora, rival source trees, silesia.tar and enwik8; it stands for a multi-GB input).
- Commands: compress `kolmo --level L -T T -f -o OUT FILE`; test `kolmo -t -T T FRAME`; `kolmo -dc -T T FRAME | sha256`.
  The frames for `-t`/`-dc` were made by main at the same level.
- Measured by `measure.py` (in the review work directory `review40b/work/exec-R06R07/`): wall time, user + system CPU
  and peak RSS and **peak memory footprint** from `/usr/bin/time -l`, and the average RSS of the kolmo process sampled
  every 20 ms. Under memory pressure macOS's maximum RSS understates the peak (level 9 on silesia.tar at `-T 1`: max RSS
  843 MB, footprint 1.34 GB), so the footprint column is the one to read.

## Level 9's one-thread peak (R07: 1.47 GiB)

A heap trace (an interposer on malloc/calloc/realloc/free recording the large allocations live at the peak, `heaptrace.c`
in the work directory) of `kolmo -9 -T 1 silesia.tar` through the file path gives a live-heap peak of 892 MiB, while
the process footprint peaks at 1.34 GB. At the heap peak:

| what is live | MiB |
|---|---:|
| the log transform's scratch, still allocated while KLZMA codes the transformed block (`log_encode_m` buffers 283 MiB, and its `zs_` cache entries 105 MiB) | ~390 |
| KLZMA's match-finder tables and encoder state for that block (son array of a 21.6 MB block, the samba member by its size) | ~277 |
| four block-sized buffers: input, transform output, slot, alternative output | ~215 |

The remaining ~450 MB of footprint is freed memory that macOS's allocator keeps dirty (R07 saw it as
"Malloc Large (empty)" in `vmmap`). Before this branch the CLI also held the whole input and a `kolmo_bound`-sized
output (about 250 MB on silesia.tar), which this branch removes. The next step for the rest is R07 #9b: free the
transform's scratch (`zs_trim()`) before the coder runs, at levels 4 and up.
