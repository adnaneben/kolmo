# rc3 wave 2, router lane: input types, levels and routes

Branch `claude/rc3w2-router-20261117`, from `claude/release-rc3-20261116` at `1536036`. Deliverables:
`docs/ROUTING-MAP.md` (type × level map, generated from this lane's measurements by `mkmap.py`),
`docs/ROUTING-PLAN.md` (what to build next), one routing fix in `src/core/blocks.c` (§3), and the GR6-L3 evaluation
(§4).

## 1. Machine, method, corpus

Cloud VM: Intel Xeon @ 2.10 GHz, 4 vCPU, 15.7 GiB, Linux; `make` defaults (`-O3 -march=native -fno-plt
-ffp-contract=off`). Tools from Ubuntu: zstd 1.5.5, xz 5.4.5, Brotli 1.1.0, LZ4 1.9.4, bzip2 1.0.8, FLAC 1.4.3,
FFmpeg 6.1.1 (FFV1 level 3, 4 slices, one thread, `-g 1`); JPEG XL 0.13.0 (lossless, effort 9) and CharLS 2.4.5
(JPEG-LS) through `imagecodecs` 2026.11.11, run in an isolated Python (`python3 -I`).

`run.py` runs one process per compression and decompression (wall time) with every tool on one thread
(`kolmo -T 1`, `zstd -T1`, `xz -T1`), four tools at a time (two for `-x`, which needs up to 5.4 GiB each), and
compares every decoded output with its input by SHA-256 (FFV1: the decoded frames against the source's frames; images:
pixel arrays). MB/s are therefore per core on a loaded machine: good for comparing tools within this run, not as
absolute speeds. `frameinfo.py` reads each Kolmo frame's index and plan prefixes and records the route (transform +
codec per block, by share of input bytes). Raw rows: `matrix.jsonl` (rc3 at `1536036`), `xnew.jsonl` (`-x` with the
§3 fix).

Corpus (`mkcorpus.py`, public downloads kept in their own directories and only read; 56 files, 505 MB, cut to 16–25 MB

## 3. Routing fix R0: `-x` alternatives

In `-x` every block is coded by CM and, as alternatives, by LZMA2 (binary) or block sorting (text). Two rules kept the
alternatives from winning where they should:

1. Blocks over 2 MiB code the alternative on a 1 MiB slice from the middle first, and code it in full only when the
   slice's rate is **3% below** CM's rate on the whole block. A slice codes worse than the block, and on table streams
   much worse: on owid-energy the LZMA2 slice was 21.6% above CM's rate, yet LZMA2 on the whole block is 1% smaller.
2. Binary blocks never tried block sorting, although `ratio`'s own slice test picks it on osdb (its slice was 11.4%
   above CM's rate; whole block 1% smaller).

Slice ratios measured with a traced build (alternative's slice rate ÷ CM's block rate; "full" = the whole-block
result against CM): owid-energy LZMA2 1.216 (full −1.0%), osdb LZMA2 1.354 (full +2.2%: rc3's LZMA2 result
2,276,454, `benchmark/rc3/bwt/RESULTS.md`), osdb BWT 1.114 (full −1.0%), mozilla's block over 2 MiB LZMA2 1.70, BWT 2.09
(full not coded), its 1.5 MB block LZMA2 1.66, BWT 1.68 (full +14%, +38%), sao LZMA2 1.001 (full +3.1%), BWT 1.054
(+10%), x-ray LZMA2 0.975 (+1.6%), BWT 0.985 (+1.9%).

**Change** (`src/core/blocks.c`): block sorting is coded in full on every `-x` block, binary ones too (10–25 MB/s,
a few percent of CM's time; when the block has a spare thread it runs beside CM, trial slot `XT_ALTB`); LZMA2
(1–2 MB/s) keeps the slice, which now has to come within 25% of CM's rate instead of 3% below it. The smallest coding
is kept as before, so a frame changes only where an alternative is smaller. Decisions depend on the input only: frames
are identical at 1 and 4 threads (osdb, owid-energy and the determinism set checked).

**Output, all 56 files at `-x`** (`xnew.jsonl` against `matrix.jsonl`): 131,185,592 → 131,155,881 bytes (−0.023%);
two files changed, both smaller, every frame decoded:

| file | before | after | change | route before → after | decode s before → after |
|---|---:|---:|---:|---|---:|
| osdb | 2,228,102 | 2,206,574 | −0.97% | CM → BWT (version 3 → 11) | 43.2 → 0.8 |
| owid-energy.csv | 831,895 | 823,712 | −0.98% | table + CM → table + LZMA2 | 27.0 → 0.1 |

`-x` now equals or beats `ratio` on every file of the corpus. `tests/test_cmpar.c` needed a new input for its
codec-25 halves case: its order-2 Markov source is now coded smaller by block sorting (122,384 against 125,364 bytes
for CM halves), which is the intended effect. The new source (each symbol depends on the one two back, a sparse
context) keeps codec 25 ahead of block sorting by 8% and of LZMA2 by 28%. Determinism set: one input changes, `stamps.i64` at
`-x` and `-x -l 2` (28,524 → 28,410 bytes, shuffle + CM → shuffle + BWT, version 3 → 11); regenerated in its own
commit.

**Time.** The `xnew` run overlapped other work on the VM (decoding unchanged frames was up to 2× slower than in the
baseline run, so its times are not comparable). Clean A/B, one process at a time, nothing else running, base and new
alternated, `-T 1`, two runs each:

| file | base s | new s | change |
|---|---|---|---:|
| webster16 (text) | 142.9, 144.2 | 147.7, 145.4 | +2.1% |
| hdfs16.log (text) | 115.1, 116.7 | 108.6, 120.9 | −1.0% |
| mozilla16 (binary, 16 MB) | 92.5, 93.6 | 97.1, 99.8 | +5.9% |
| sao (binary records) | 23.6, 23.3 | 23.5, 22.9 | −1.2% |
| mozilla16, `-T 4` | 51.8, 66.0 | 54.5, 49.2 | within noise |

At one thread the full block-sorting pass costs up to 6% (mozilla); text blocks pay about 2% (the pass that the slice
used to skip); at four threads it runs beside CM and the difference is below this VM's noise. Decoding is unchanged
except where a frame changed (osdb and owid-energy now decode 50-270× faster: block sorting and LZMA2 instead of CM).

## 4. GR6-L3 (`lzp` phrases, level race) against rc3 `-x`

against the vendored zstd): level 1 letters, level 2 words (GR6+), level 3 dictionary-free `lzp` phrases, chosen by a
race on a sample. It was run with policy `auto` (the race), `lzp` (levels 1+2+3) and `none` (levels 1+2), one

GR6+ is already chosen, by 0.06% and 0.54%, and that comes from its word level (same with and without `lzp`), not from
the phrases. The race is not needed inside `-x` either: codec 26 is already tried in full and kept only when smaller.

## 5. Experiments behind the plan

**Colour transform for 8-bit RGB images** (`rct` estimate, plan item 1). Order-0 entropy of median-predictor
residuals per channel, plain RGB against G, R−G, B−G and against YCoCg-R, four Kodak photographs: 3,052,752 →
2,132,872 bytes (−30.1%) and 2,123,240 (−30.4%). Kolmo's IMG8 output on the same images (`balanced`, 2,930,758
bytes) is close to the plain-RGB estimate, so the transform carries over; JPEG XL e9 is 1,793,567 bytes.

**`balanced` block count** (plan item 5; rc3, `-T 1` encode; decode at `-T 4`):

| file | ~8 blocks (default) | one block (`-B 16`) | change | decode 4 threads |
|---|---:|---:|---:|---|
| gharchive16.jsonl | 2,043,341 | 1,934,271 | −5.3% | 18 → 65 ms |
| webster16 | 4,951,204 | 4,906,656 | −0.9% | 24 → 80 ms |
| samba16 | 4,207,152 | 4,059,780 | −3.5% | 44 → 72 ms |
| enwik8_16 | 6,045,983 | 5,994,939 | −0.8% | 38 → 63 ms |

**FASTQ at `ratio` vs codec 16** (plan item 4), SRR062634 24 MB, quiet machine: `ratio` 5,479,320 bytes, 2.8 s /
2.7 s (1 thread), 2.1 s / 1.2 s (2 threads); `-x` (codec 16) 4,908,324 bytes (−10.4%), 9.1 s / 10.0 s and
4.8 s / 6.0 s.

**x86 filter on mozilla** (not chosen by the planner): xz -9e 5,937,932, with BCJ 5,975,740 (+0.6%); libLLVM 16 MB
2,052,032 → 2,108,444 (+2.7%). No miss.

**bf16 weights at `-x`** (plan item 11): CM 29,899,782 bytes in 208.6 s against `ratio` 30,120,753 in 6.6 s
(−0.73% for 32× the time).
