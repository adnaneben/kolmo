## 1. What was built and why

rc3 codes every graph leaf with an order-0 coder (Huffman, rANS) or an LZ/BWT codec, and 16-bit image blocks as two
byte planes under zstd or BWT. Stage 1 measured that image residuals are much cheaper under the magnitudes of their
already decoded neighbours (bounds −13% to −16% at `balanced`), which is how the fast lossless image coders work
(JPEG-LS's gradient contexts, JPEG XL's modular mode). There was no coder between "order-0 bytes" and "LZMA / BWT /
CM". This work adds one.

### 1.1 The coder (`src/algo/krans.c`, 588 lines; format in the header comment of `src/algo/krans.h`)

- **rANS**: 32-bit states in [2^16, 2^32), totals 2^12, renormalisation by 16-bit words (at most one per symbol each
  way), encoder by reciprocal multiplication. Method: Duda, "Asymmetric numeral systems: entropy coding combining
  speed of Huffman coding with compression rate of arithmetic coding" (arXiv:1311.2540); several states in one word
  stream: Giesen, "Interleaved entropy coders" (arXiv:1402.3392). The code is written for Kolmo; nothing is copied.
- **Segments instead of position-interleaving**: a chunk is cut into S = 1..32 contiguous segments, one state each;
  the decoder takes byte i of every segment in turn. A byte's context only looks back inside its own segment, so the
  S context chains are independent (instruction-level parallelism now, SIMD lanes later). Cost: the first row of a
  segment has no row above it; the encoder keeps at least 8 rows per segment.
- **Integrity for free**: the encoder starts every state at 2^16; a chunk is valid only if every state returns to
  2^16 and the word stream is used up exactly.
- **Contexts** = (bin of e) × (bin of the previous byte) × phase:
  e = sum of the magnitudes of up to four earlier bytes at lags given in the chunk header (for an image: left, up,
  up-left, up-right of the same channel), binned in 17, 9 or 48 bins; the previous byte either as itself (order 1),
  as a 6-bin magnitude, or as an 11-bin magnitude with sign (for interleaved RGB the previous byte is the previous
  channel of the same pixel; a header bit drops the term in phase 0, where it would be another pixel); phase = byte
  position modulo P (channel, or byte of a word). At most 4096 contexts.
- **Context map**: the contexts are merged onto at most 255 frequency tables (greedy clustering on exact counts, one
  reassignment pass, exact score = header bits + code lengths with the quantised frequencies); the map is run-coded.
  Tables are coded as magnitude classes against the previous symbol's class with 3, 4, 6 or 12 mantissa bits; one
  symbol per table takes what the others leave of 2^12, so a table always sums exactly.
- **16-bit words (`mk` 3)**: bytes are (high, low) pairs of zigzag residuals; the lag terms are half-octave classes
  of the neighbouring words; the low byte is also coded under its high byte.
- **Chunks**: stored, fill (one byte value) or coded; 128 KiB without geometry, 2 MiB with (cut on whole rows per
  segment); a leaf is self-contained (lags and phase period are in each chunk header).
- **Encoder choice per chunk**: order 0 always; then, with geometry, the image set (effort 2 also tries the set
  whose previous-byte term stays on in phase 0 and the 9-bin energy quantiser; 16-bit: order 0 per byte of the word, the word
  contexts, at effort 2 the 48-bin quantiser), otherwise order 1 for chunks ≥ 2048 bytes; the smallest exact score
  wins; a chunk that does not shrink is stored.
- **Decoder**: scalar C. The unchecked inner loops are instantiated for the shapes the encoder writes (order 0,
  order 1, four neighbours, four neighbouring words, eight states) with the states in registers, plus one general
  loop; segment starts and the end of the word stream go through one checked routine. Every table is validated (sum
  exactly 2^12, classes in range, first/last symbol present), every read and write is bounded.

### 1.2 Leaf codec 33 (`src/codecs/krans_leaf.c`, hooks in `src/transforms/graph.c`)

With the opt-in, `kg_serialize` (every graph leaf) and `kg_sel_sub` (sub-streams of the per-plane and zero-run
leaves 21 and 23) code the leaf with codec 33 as well and keep it **only when it is smaller** than the leaf rule's
choice. The IMG8 node passes its row length and channel step, so the residual leaf gets the neighbour contexts;
other leaves get order 0 and order 1.

### 1.3 Block codec 34 (`src/codecs/krans_leaf.c`, hook in `src/core/blocks.c`)

A block with the 16-bit image transform (flag 6) is a 12-byte header, a low-byte plane and a high-byte plane. Codec
34 stores header, skip and trailing bytes and codes the residuals as (high, low) pairs with the 1.1 coder under the
word contexts. The block worker tries it beside the block codec and keeps the smaller; the decoder rebuilds the
transformed stream and the unchanged image inverse runs.

### 1.4 Design choices and the alternatives rejected

| choice | alternative | evidence |
|---|---|---|
| one context formula with header fields (lags, bins, phase) | three hard-wired modes (stage-1 plan) | the same decoder serves order 0, order 1, 8-bit images, 16-bit words and any fixed-stride leaf; new context sets need no new id |
| context map onto shared tables | one table per context, or "share the order-0 table" (stage-1 plan) | tables are the cost of a static coder: stage 1 measured 18,758 bytes over the bound for an order-1 coder on astronaut. Final leaf, `$W/final/kernel.txt`: astronaut 353,181 bytes with the image set against 390,550 order 1 and 434,019 order 0 |
| previous channel with sign, 11 bins (`bq` 3) | magnitude only, 6 bins | astronaut 368,874 → 353,320, coffee 383,639 → 362,896 (commit message `b9546117`) |
| stop there | finer signed bins, or a second previous channel | under 1% either way (commit message `b9546117`): not in the format |
| 2 MiB image chunks | 1 MiB | retina 1,005,562 → 1,002,227, hubble leaf 1,434,052 → 1,430,702 (commit message `b9546117`) |
| run-coded context map | plain indices | 600 bytes of text: 306 → 217 bytes coded (commit message `b9546117`) |
| at least 8 rows per segment | always 8 states | coins residual leaf 68,390 bytes (commit message `e1482a9b`) |
| per-shape decode loops, cold set-up code | one generic loop / everything `-O3` | object text 61.0 KB → 29.0 KB (commit message `82ce52e2`); today `size build/obj/src/algo/krans.o`: 35,449 bytes with the word run |
| branch-free refill written as xor/and | `x = lt ? y : x; p += 2 * lt` | **negative**: GCC 13 turns the ternary into branches. `$W/final/kernel_refill.txt` (indicative): decode 168.7 → 134.3 MB/s (retina leaf), 184.0 → 128.4 (mr block), 554.7 → 188.5 (order 0). Kept the xor/and form; the variant is `$W/final/krans.ternary-refill.c` |
| four neighbour lookups per byte in the symbol loop | the three upper neighbours summed for a batch of positions first (a loop the compiler could vectorise), the symbol loop adds the left one | **negative as written** (prototype `$W/final/krans.far-prototype.c`, not on the branch; it passes `tests/test_krans.c`): decode 164.8 → 90.0 MB/s on the retina leaf and 180.4 → 96.1 on coins (`$W/final/kernel_far.txt`, indicative). GCC 13 did not vectorise the batch loop and kept the states in memory. The same prototype folds the previous-byte term and the phase into one per-phase table, which helped the order-1 loop (223.8 → 327.3 MB/s in that run): a small follow-up, not applied because the tables above were already final |
| word run that carries three of the four neighbour classes | generic word loop | part of commit `89d62b8e` (first attempt; no separate figure survives, so none is claimed) |
| a chunk under 256 bytes has one context (commit `1062b9e3`) | no rule | a valid leaf of one-byte chunks with 3,696 contexts each cost 5.64–5.92 µs per chunk to decode (2.70–2.84 MB/s of input) and 2.19–2.49 µs with one context; after the rule the first is refused and the second costs 0.06 µs (216–224 MB/s). `$W/final/tinychunks.c`, `tiny.txt`, 3 runs each through measure.py, indicative. The encoder never wrote contexts below 2048 bytes, so no stream it chose changes |
| static tables | adaptive rANS / binary models | out of scope of the claim (R05's and my planned CM claims); static tables keep the decoder a table lookup and a multiply |
| scalar decoder first | AVX2 gather kernel now | not responsibly finishable and verifiable tonight on one x86 machine with no ARM build; it is the first follow-up (section 9) |

## 3. How to use it

    KOLMO_NATIVE=rans kolmo -m balanced in out      # also eco, hc, ratio; combinable: KOLMO_NATIVE=rans,lz,...
    kolmo -d out back                               # decoding needs no switch

`rans` is not part of `KOLMO_NATIVE=all`. There is no CLI flag: the other `KOLMO_NATIVE` roles have none either.
Library users set the environment variable before the first call (it is read once).

- **Decode is the cost.** With image contexts the scalar decoder runs at about 155–185 MB/s warm (12–14 cycles
  per byte at 2.1 GHz; my reading of the loop, not a measurement: it is bound by instruction count, roughly 45 per
  byte for the four neighbour lookups, the context arithmetic, the table lookup and the branch-free refill, not by
  the dependency chains), and end to end the
  image files decode 2.7× (retina 279 → 104 MB/s), 3.4× (mr) and 4.3× (x-ray) slower than rc3's zstd/Huffman path at
  `balanced`. At `hc` the ratio is 1.8× to 2.6×. For scale, the in-process times `rivals16.py` printed for the same
  pixels (not through measure.py, one run, so only a rough guide): JPEG-LS decode 0.071 s (mr) / 0.105 s (x-ray),

- **Encode**: 2.5× (retina) to 5–7× (mr, x-ray) slower at `balanced`, where the base is a level-3 zstd; +5% to +34%

  bytes); encode +0.5 to +3 MiB at `balanced`, about +14 MiB sampled at `hc` on the 16-bit files (the trial's
  buffers: 2 bytes of scratch per chunk byte for the word stream, 2 for the contexts, counts for up to 4096
  contexts). The decode figure of codec 34 is declared by `blk_dec_need` (base + transformed length + 2 MiB); the
  encoder's trial buffers are **not** registered with the memory governor's estimates.

## 5. Format and compatibility

- **New identifiers only**: leaf codec 33 (graph leaves, also as a sub-codec inside 21 and 23) and block codec 34
  (valid only with transform flag 6). Ids 30–32 are left to the w4-entropy lane and R01.
- **Written only with `KOLMO_NATIVE=rans`.** Without it: byte-identical output to rc3 on all 128 measured
  file/mode pairs, and `python3 benchmark/determinism/check.py build/kolmo DIR` → "122 frames checked; OK" against the
  repository's `expected.sha256` (which this branch does not touch).
- Frames holding 33 or 34 are container version 11, as for the other `KOLMO_NATIVE` coders. The rc3 binary refuses
  them cleanly ("corrupt or unsupported input"; `rc3_refuses` rows). With the opt-in set, a frame in which neither
  codec was kept still carries version 11 (existing behaviour of every `KOLMO_NATIVE` value, `blocks.c` line 561)
  and rc3 decodes it (`rc3_decodes` rows).
- rc3 frames: nothing in their decode path changed; `make check` (legacy frames in `kolmoresource`), `check-format2`
  and `check-native` pass.
- The chunk format is pinned by a golden stream (`tests/test_krans_golden.h`). One rule was tightened before any
  release (`1062b9e3`: contexts need 256 bytes); it invalidates no stream the encoder writes by its own choices.
- SPEC.md carries both codecs; the normative text of the chunk format is the header comment of `krans.h`.

## 7. What was NOT verified

- **Speed on the owner's M5, and any ARM build at all.** The code is portable C (GCC/Clang builtins
  `__builtin_clz`, `unsigned __int128` in the encoder) but was compiled and run on x86-64 Linux/GCC 13 only. No
  big-endian run (the format is defined byte-wise; the code reads through byte-order-independent helpers).
- **No SIMD kernel.** The claim's AVX2/NEON follow-ups are not written; all speeds are the scalar decoder.
- Multi-thread timing, and timing at `ratio` / `-x`. `-x` with the opt-in was only run on the six files of `x.tsv`
  (round trip OK, sizes unchanged); `tests/test_krans_modes.py` does not include `-x`.
- The Python and Rust bindings: source lists updated, not built.
- Coverage-guided fuzzing: the decoders were only attacked by the random corruption in the tests above (under
  ASan/UBSan), not by a fuzzer with coverage feedback.
- Worst-case decode time after the 256-byte rule was measured for one-byte chunks only; a leaf of 256-byte chunks
  that each declare thousands of contexts pays the measured set-up cost (5.6–5.9 µs before the change) once per 256
  bytes; I did not build that stream.
- The encoder's trial memory is not in the governor's estimates (section 4.4).
- `rivals.tsv` (8-bit rivals) was produced in the first attempt by `rivals.py` and not re-run now; the JPEG XL e7/e9
  figures for mr and x-ray re-measured now equal R05's recorded ones.
- WebP lossless streams were not decoded back by the script.
- Only 17 photographs/renders and two 16-bit medical images were measured; no large photographic set, no CMYK or
  alpha images, no 16-bit colour.

## 9. Next steps

Under #11 / #17 (mine):

1. **Decode speed.** (a) the per-phase previous-byte table of the prototype in 1.4 (order 1: +10% or more,
   indicative); (b) a working form of the batched upper-row sums (the first prototype is slower, 1.4); (c) SIMD
   kernels (AVX2 gather over the 8 states, NEON): my estimate from the gather count (ten per round of eight bytes
   with image contexts, three for order 1) is that they help order 0/1 much more than the image shape, so the
   2.7–4.3× end-to-end penalty on image blocks will shrink, not disappear. A static context coder at this modelling
   depth is in JPEG-LS's speed class, not Huffman's; that trade is the owner's to judge.
2. **A default is the owner's decision, not made here.** If wanted for images at `balanced`, it needs (a) the M5
   numbers, (b) kernel 1, (c) a size gate (the leaf rule asks 3% of order-0 rANS today; images gain 10–30%).
3. **Encoder gate**: skip the order-0/1 trial on leaves where a sampled order-1 entropy cannot beat the chosen codec
   (removes the 3.5× compress cost on float arrays for a 1% gain).
4. mr: per-slice restart of contexts and prediction belongs to R05's planned `img16-cm-model`; codec 34 would
   benefit from the same slice detection (a segment boundary per slice).
5. Planned #59 `img8-trial-krans-score`: patch and numbers ready (above); needs a stage with it as an execute claim.
