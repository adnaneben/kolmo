## 2. How the tier works, and what the code review found

`ratio` (`-m max`) sends text blocks (`looks_text`: 95% printable in four 16 KiB samples) straight to codec 18;
binary blocks are coded with LZMA2 and block sorting is tried when LZMA2 reaches 35% or less (slice-gated above
8 MiB, must win by 3%); transformed blocks may fall back to block sorting of the plain bytes. Codec 18 is
LZP (hash 17 bits, minimum match 96) -> BWT (libsais subset, sampled indexes for a threaded inverse) -> adaptive
QLFC in coder parts of at least 4 MiB. Block size is the whole file up to 128 MiB.

Findings:

1. **The tier is libbsc in C.** `lzp.c`, `qlfc.c`, `qlfc_model.h` (every model constant), `rangecoder.h` and the
   block driver are ports of libbsc 3.4.0, `sais/` is a libsais subset (both Apache-2.0, credited in the headers).
   Codec 18 differs from `bsc -e2` only by parameters: LZP 17/96 instead of 15/72, coder parts >= 4 MiB, no 28-byte
   header. At an equal block the two are therefore the same compressor: dickens 2,254,558 vs 2,259,136 B, -0.20%
   (recorded, `benchmark/w4/bwt/RESULTS.md`). `ratio`'s lead over `bsc -b25` on enwik8 (-6.75%, recorded) is the
   block size, not the coder (my block-size measurement below: -B 32 costs +5.6%). **Kolmo has no block-sorting
   entropy stage of its own.** For a compressor that must win with its own engine this is the central gap of my
   lens, and it is also where bzip3 (direct context mixing of the BWT) is ahead on some data (finding 4).
2. **Content segments regress samba by 6.3% at `ratio`** (measured, section 3.1). `content_segments()`
   (`src/plan/segment.c`, twopass lane, in rc3) cuts a non-archive file into runs of one 64 KiB-window class. samba
   is a tar of 1,573 small members, so `mt_tar` yields no member segments, the content cutter then splits it into 7
   runs, each coded alone, and the repeats between runs are lost: 3,975,940 B against 3,739,524 B for the same build
   with `-n` (one LZMA2 block). The rc3 bwt lane recorded exactly 3,739,524 for samba before the twopass merge
   (`benchmark/rc3/bwt/RESULTS.md`), so this is a regression of rc3 itself. It is also the only Silesia file on which
   `bsc -m0 -e2` (3,909,928 B, recorded) beats `ratio`. The twopass tests used samba only inside a concatenation.
   Every source tarball of small files is exposed to this.
3. **Fixed LZP parameters cost up to 1.5% on repetitive structured text** (measured, 3.3): xml is 1.50% smaller
   with LZP off, nci 1.06% smaller with minimum match 255; prose does not care (+-0.06%); samba wants 96.
   The stream already carries the LZP parameters, so a per-block choice needs no format change.
4. **QLFC (rank/run coding) is weaker than direct modelling on numeric and binary BWT data** (measured with a cost
   prototype, 3.4): -3.8% on mr, -2.3% on x-ray, -1.4% on osdb with an untuned model; prose within +0.2..0.5%.
   Recorded rival evidence points the same way: bzip3 -b 16 is 0.91% smaller than `ratio` on dickens
   (`benchmark/w4/entropy/results/ratio_tables.md`), and on the 18 8-bit images bzip3 is at +17.0% of `-x` where
   bsc is at +23.2% and `ratio` at +17.4% (`benchmark/rc3/leaders/RESULTS.md`).
5. **`ratio` drops the word transform before block sorting and has no text transform designed for it** (tracker
   R12, not done). A prototype of one gains 1.47% on dickens and shrinks the sort input by 28% (measured, 3.5).
6. **Blocks above 128 MiB are sorted independently**; on enwik8, 32 MiB blocks cost +5.61% and 16 MiB +9.21%
   (measured, 3.6). enwik9 (recorded 180,020,338 B) pays this; it cannot be measured in this container.
7. Smaller points, no claim: (a) the sampled-index table is always libbsc's 8 to 15 entries, 32-60 bytes even for
   a 10 KiB graph leaf (folded into the planned `bwt18-enc-params`); (b) `bwt_stream.c` includes `qlfc.h` twice and
   `bwt.c`'s comment says XXH32 where the code truncates XXH64 (cosmetic); (c) with `-n`, x-ray is coded by LZMA2
   at 4,491,263 B although block sorting gives 3,750,782 (-16.5%, measured): the "LZMA2 must reach 35%" gate hides
   it; the default path is not affected because the image transform is used; (d) `kmem_enc_codec` charges 6n+8 MiB
   for codec 18 while the w4-bwt lane brings the working set to 4n: the estimate should follow when that lane lands.
8. **Tar member segments have the same loss as finding 2** (measured, 3.7). mozilla at `ratio` is 13,909,331 B in
   33 member blocks, 32 of them plain LZMA2 with no transform; the same bytes as one LZMA2 block are 13,376,235 B
   (-3.83%), which is also what xz -9 writes (13,374,160, measured here). Members that end up with the same plan and
   coder gain nothing from being separate blocks and lose the repeats between them. Planned claim
   `archive-member-seg-merge` (the same merge pass as the guard). Seen in passing and **not claimed by me**: none of
   mozilla's members gets the x86 filter (every plan prefix is 0,0,0,0); whoever owns the executable filter should
   look.
9. Security: both codec-18 decoders I read are bounds-checked (decoded size against the output, runs against what
   is left, exponent loops capped, range decoder end pointer, index count against the stream). I found no unchecked
   read or write. The new coder I propose must meet the same bar (fuzzed under ASan in `check-bwt`).

### The w4-bwt lane (unmerged)

No format change, frames identical (its claim; I did not rebuild it). Huge pages for the suffix and PSI arrays,
4n working set (LZP and BWT in the caller's slot, QLFC into the freed suffix array), an unrolled LZP encoder, and
the dead word transform skipped. Review notes: the in-place encoder and decoder paths look correct (QLFC output
capacity `asz >= lz + 64`; LZP output is always below n so decoding into `out` is safe); `kolmo_big_free` needs
the allocation size and every exit path passes it. Two things for integration: (1) its change 4 (skip
`word_encode` when the coder reads raw bytes) is the same edit as claim #9 (R07): one of them should land, not
both; (2) my codec 36 reuses codec 18's front end, so I will keep the new coder in its own function to avoid
conflicting with the lane's rewrite of `kolmo_bwt_compress`. The lane's own conclusion is that QLFC is 45% of
codec 18's encode time and 91% of decode instructions: the entropy stage decides the tier's speed as well.

## 5. Plan

### 5.1 `ratio-content-seg-guard` (execute, primary)

- **Design.** When `content_segments()` returns more than one run, compute for each run the share of its bytes that
  repeat content of *other* runs (one pass, hash of 32-byte windows at sampled anchors, verified by comparison and
  extended; `xrep.c` is the prototype). Runs whose share is above a threshold are merged with their neighbours (the
  file stays whole when all are); runs that share nothing (the twopass four-kinds case) stay cut. The rule reads the
  input bytes only, so frames stay deterministic and independent of `-T`. At `ratio`, where the probe is inside an
  undecided band, both codings are produced and the smaller kept. Thresholds come from a sweep, not judgement:
  samba (6.96% share, segmenting loses), the twopass mixed file (segmenting wins), concatenations of Silesia members.
- **Files.** `src/plan/segment.c`, `src/core/compress.c` (call site), tests, `docs/TWOPASS.md` (new dated note, the
  historical text stays).
- **Expected gain and basis.** samba at `ratio`: 3,975,940 -> at most 3,739,524 (-5.95%), measured by `-n`. hc and
  balanced on samba to be measured with segmenting switched off in a patched build (the CLI has no switch for it).
- **Risks.** Format: none (segments are a planning unit; rc3 reads the result). Speed: one extra pass over files
  that are cut at all (rare), plus a second coding in the undecided band at `ratio` only. Memory: a 16 MiB anchor
  table while planning. Default bytes change on affected files (samba): **flagged loudly**; I will ship it behind a
  switch (environment variable / parameter) and state the evidence so the owner can make it the default.
- **Success.** samba `ratio` <= 3,739,524 with the round trip checked; the twopass mixed file keeps its recorded
  gain; every other corpus file byte-identical to rc3 (SHA-256 of frames); determinism at T=1 and T=4.

### 5.2 `bwt-direct-cm` (execute)

- **Design.** `src/algo/kbcm.c`: the BWT bytes are coded directly, most significant bit first, with a binary
  arithmetic coder. Predictions come from BWT-domain contexts only (orders 0-3 of the preceding BWT bytes, the
  current run length class, the agreement pattern of the last three symbols), two counters per context (fast and
  slow), mixed by two small logistic mixers (selected by run class and by the previous byte) and refined by
  interpolated APMs; integer arithmetic only, so every platform writes the same bytes. Long runs (xml, nci,
  logs) get an explicit run model: after a run of r equal bytes one binary "run continues" decision in a
  (byte, run class) context replaces the 8 bit decisions, which is what the prototype lacks on xml. Coder parts
  by a size-only split so the stage decodes on threads, like QLFC. New codec id 36 = codec 18's header and
  LZP/BWT front end with this coder; written only on request and then kept per block only when smaller than
  codec 18.
- **Originality.** Written from the model description above; no code from bzip3, BCM, lpaq or libbsc. Ideas in the
  open literature: logistic mixing (Mahoney, "Adaptive weighing of context models for lossless data compression"),
  secondary estimation, direct modelling of BWT output (Fenwick, "Block sorting text compression").
- **Files.** `src/algo/kbcm.c/.h` (new), `src/codecs/bwt.c`, `bwt_stream.c/.h`, `codec.h`, `codec.c`,
  `src/core/blocks.c` (the opt-in trial), `src/core/memneed.c`, `tests/test_bwt.c`, `SPEC.md`, `research/CODECS.md`.
- **Expected gain and basis.** Section 3.4: -3.79% mr, -2.26% x-ray, -1.38% osdb as ideal code length; the
  real coder adds a few bytes of termination per part. Aim on prose: not larger than codec 18 after the run model
  and tuning (today +0.17..+0.52%); if it stays larger, codec 18 is kept for those blocks (the per-block choice
  makes the result never larger when the option is on).
- **Risks.** Speed: 8 binary decisions per non-run byte against about 2 per run in QLFC, so decode per thread will
  be slower (bzip3's recorded 8-10 MB/s against QLFC's 20-25 gives the order); measured with `measure.py`, labelled
  indicative, re-measured on the M5. Memory: tables of a few MiB per part (order 2 exact 2^24 x 2 counters, order 3
  hashed), bounded and declared in `memneed`. Format: new id 36, container version note, rc3 frames untouched,
  rc3 decoders refuse id 36. Binary size: one small file.
- **Success.** Real round-tripped bytes below codec 18 on mr, x-ray, osdb (and on the image-residual stream `ratio`
  actually sorts for mr) by at least the prototype's margin minus 0.2 points; never larger with the per-block choice;
  corrupted and truncated streams rejected under ASan/UBSan; identical bytes at 1 and 4 threads.

### 5.3 Planned (owned, not built tonight)

- `archive-member-seg-merge`: after planning, adjacent segments of any origin with the same plan type and coder
  class become one planning unit up to the block size (mozilla: 13,909,331 -> 13,376,235 expected, measured by the
  one-block run). It is the same pass as 5.1's merge, so it goes into that patch series if the sweep supports it.
- `bwt18-enc-params`: choose LZP off / 17-96 / 17-255 per block from the LZP pass's statistics (validated against
  exact double coding), no sampled indexes on blocks the inverse does on one thread. rc3-decodable. Gain: xml
  -1.50%, nci -1.06% measured; cost: possibly a second sort where the predictor is unsure.
- `bwt-text-xform`: section 3.5 as a C transform with an escape scheme; new tflag.
- `ratio-text-block-budget`: block from the memory budget for block-sorted text above 128 MiB.
- `xseg-long-range-rep`: long repeats that reach outside the segment/block as a side stream.
- `bwt-context-tree-coder`: cost prototype first (go/no-go against codecs 18 and 36), then a decoder.
