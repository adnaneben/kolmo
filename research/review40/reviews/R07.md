| tool | what it gives | where |

Every compress in the tables was decoded with the rc3 binary and compared with `cmp` (column "RT").
Allocation totals ("allocated") count requested bytes, so they can exceed the resident set where pages are never
touched; the RSS columns are the resident truth.

### 3.2 Where the encoder's peak is (allocation maps, `mt.sh`)

`MT_OUT=log LD_PRELOAD=mtrace.so setarch -R kolmo MODE -T 1 file out`, live set at the moment of the largest total.

**dickens `-m ratio`** (9.72 MiB input; 113.7 MiB allocated at the peak, 103.4 MiB resident):

| MiB | call site | what it is |
|---:|---|---|
| 48.4 | `kolmo_bwt_compress` (2 blocks) | work copy n + suffix array 4n: the block-sorting stage, needed |
| 24.0 | `zs_malloc < word_encode` | the word transform's 2^20-entry table (`went_t`, 24 bytes each), still in the thread's scratch cache during the whole sort |
| 21.9 | `compress_worker` (2 blocks) | `tbuf` (block + slack) and `slot` (output bound) |
| 9.7 | `read_input < main` | the CLI's copy of the whole input |
| 9.7 | `main` | the CLI's output buffer (`kolmo_bound`) |

The word-coded copy written into `tbuf` and the 24 MiB table are **dead work on this path**: `blocks.c` codes the
transform (`pl.t == T_WORD`: `word_encode(raw, len, tbuf, ...)`, `tflag = 9`) and a few lines later throws it away
(`else if (codec == C_LZMA && (!tflag || tflag == 9) && looks_text(raw, len)) { codec = C_BWT; if (tflag == 9) { in = raw; ... } }`,
and for `-x`: `if (codec == C_CM && tflag == 9) { in = raw; ... }`).
Upper bound of what removing it gives, measured with the existing `-n` switch (no analysis, so no word plan; the
payload has the same length, only the 4 plan bytes of the block differ, so the frames are not byte-identical and `-n`
is not the fix): `measure.py --runs 3`, dickens `-m ratio` peak 103.4 / 103.4 / 103.5 MiB, average 66.8 to 68.9;
`-m ratio -n` peak 61.7 / 61.6 / 61.7 MiB, average 39.0 to 40.7 (both 2,254,558 bytes). webster, whose plan is not
the word transform at ratio, shows no difference (242.2 against 241.0 MiB), so the saving is confined to blocks that
were planned as words.

**enwik8 `-m ratio -l 1`** (95.4 MiB input; 902.1 MiB allocated at the peak, 663.6 MiB resident): block sorting
472.8 (work copy + suffix array), worker `tbuf` + `slot` 214.6, CLI input 95.4, CLI output bound 95.4, word table
24.0. The word transform ran here too (its table is in the live set), so the table and whatever part of `tbuf` the
word-coded copy touched are dead; my tools do not separate the resident part of `tbuf`, so for enwik8 the removable
amount is between 24 MiB (the table alone) and about 95 MiB (table + a fully touched word-coded copy).

**dickens `-m hc -l 9`** (75.9 MiB allocated at the peak, 60.9 resident): word table 24.0, `tbuf`+`slot` 21.9,
zstd context 10.5, CLI input 9.7, CLI output 9.7. Here the word-coded bytes are the coder's input, but the 24 MiB
table is no longer needed once `word_encode` has returned.

**dickens `-m eco`** (140.5 MiB allocated, 103.9 resident): Brotli 41.6 + 32.1, word table 24.0, `tbuf`+`slot` 21.9,
CLI input 9.7, CLI output 9.7.

**Loghub, 16 x 2k lines concatenated (4,458,875 bytes; `/home/user/kolmo-review40-data/R07-logs`, URL and SHA-256
recorded there)**:

|---|---:|---:|---:|---|
| `-m balanced` | 316,254 | 27.4 | 14.6 (9 arrays) | CLI in/out 8.6, worker 2.3 |

### 3.3 The CLI keeps the whole input and a whole output bound in memory for eco, hc, ratio and -x

`src/cli/cli.c`: `if (!range && (dec || P.mode == KOLMO_FAST || P.mode == KOLMO_RT))` sends only decode, speed and
balanced to `process_file` (fd in, staged fd out, blocks read with `pread`, written in order with `pwrite`). Every
other compress does `read_input` (malloc of the file size) and `malloc(kolmo_bound(n))`. The library function the fast
modes use, `kolmo_compress_file`, takes any mode. Experiment (`filepath.c`: that function, same parameters as the CLI,
one thread), against the CLI rows of section 3.1:

`-x` through the same function, checked on two small inputs only (it is slow): first 100 KB of dickens, 27,665
bytes, SHA-256 `221b6207499bdb66...` from both paths; first 300 KB of mozilla, 143,751 bytes, `a0d29cfdeb3ac29c...`
from both; both decode to the input. The dickens rows above were compared by size and round trip, not by hash.

So the existing fd path already writes the identical frame in the slow modes; on an input of one block it changes
nothing (the block copy replaces the input copy), and on a multi-block input it removes the term that grows with the
file. That term is unbounded: at `-m ratio` a 4 GB file needs 4 GB + its output + the block working set today, where
the working set of one 128 MiB block is all the fd path needs per thread. What remains in the fd path at `hc -l 9`
(180.9 MiB) is dominated by the log transform's scratch on the nci member (3.2), i.e. by the transform stage
(claims #9 and #20), not by I/O.

### 3.6 The governor's encode estimates against the measured peaks

From `kmem_enc_block` (read from the source, then evaluated by hand for the block sizes above; not a measurement):
dickens at ratio reserves about 244 MiB (2 x (len + slack) + 2 x slot + 4 MiB = 47.8, plus the larger of LZMA2
12 x 16 MiB + 4 = 196 and block sorting 6n + 8 = 66) for a job whose whole process peaks at 103 MiB; enwik8 about
1,205 MiB (433 + 772) against 664 MiB. (My first hand evaluation gave 239 and 1,158 MiB; those two figures are in the
text of claim #21 and are corrected here: the slack term was left out.)
The transform stage is not in the estimate at all (8.6 x block for logs), and
`benchmark/rc3w2/memdyn/RESULTS.md` section 4 already records `-x` under `-M 256M` peaking at 372 MiB while encoding.
Over-reservation only costs concurrency when memory is short; under-reservation lets the governor over-commit. A
planned point, not an execute one: at 4 threads on this 15 GiB machine neither binds.

## 5. Plan

### 5.1 `cli-slow-modes-fd-path` (claim #8, execute tonight)

**Design.** (a) `cli.c`: send eco/hc/ratio/-x compress of a regular file of at least the existing 8 MiB threshold
through `process_file` / `kolmo_compress_file`, exactly as speed and balanced go today; keep the buffer path for
stdin, `-r`, `-P` (profiles), `--target` and small files. (b) `compress.c`: the fd path maps the whole file for
planning (`mmap` + `MADV_RANDOM`) and unmaps it before the blocks run; make the planner's file-backed resident pages
bounded for large inputs by dropping the pages behind the scans (`madvise(MADV_DONTNEED)` on the windows
`meta_segments`, `content_segments` and the WAV/AIFF probe have finished with; file-backed, so nothing is lost) and
check the Y4M route (it maps the file itself). (c) `blocks.c`: per-worker `input` is `malloc(J->B)`, the largest
block; allocate lazily and size it to the largest block the worker actually takes when blocks differ widely (tar
members). (d) Leave out-of-order output (`emit_block` copies) alone: claim #7 bounds it.

**Files.** `src/cli/cli.c`, `src/core/compress.c`, `src/core/blocks.c`, `src/core/io.c`, `src/api/api.c` (comments
only unless needed), `tests/` (new identical-frame test), `docs/MEMORY-MODEL.md` (as-implemented row).

**Expected gain and basis.** Section 3.3, measured with the unmodified library: -27% to -57% peak and -37% to -53%
time-average RSS on silesia.tar, identical frames. On inputs of one block: none (stated, measured).

**Risks.** Format: none (execution only; identical frames are the acceptance test). Speed: the fd path copies each
block once with `pread` instead of `fread` once, and writes with `pwrite` instead of one `fwrite`; expected neutral,
to be measured with `measure.py --runs 3` (the rc3 comment says the file path loses below 8 MiB on macOS, hence the
same threshold). Memory: none negative expected; single-block inputs unchanged. Behaviour: the output is staged in a
temporary file next to the destination and linked, as speed and balanced already do; an unwritable directory falls
back to `tmpfile()` as today. Binary size: a few lines.

**Success is measured by.** (1) SHA-256 of every frame equal to the rc3 binary's for 6 modes x (12 Silesia members,
silesia.tar, enwik8, a 3 x silesia.tar concatenation of 636 MB) at -T 1 and -T 4, and decode == original;
(2) `measure.py` peak and average RSS, new against rc3, same table as 3.1, with the 636 MB input showing that the
peak no longer grows with the file; (3) wall time not worse beyond noise (3 runs each, labelled indicative);
(4) `make check` and the determinism check pass in my worktree.

### 5.2 `enc-transform-stage-memory` (claim #9, execute tonight)

**Design.** In `compress_worker`: (a) before the transform switch, when `pl.t == T_WORD` and the block's coder will
read the raw bytes anyway (`J->codec == C_CM`, or `J->codec == C_LZMA && (level == 1 || looks_text(raw, len))`,
the exact conditions under which rc3 later resets `in = raw`), do not call `word_encode`; the 4 plan bytes
(`slot[0..3]`) are written exactly as rc3 writes them, so the frame is byte-identical. (b) After the transform
stage and before the coder call in eco/hc/ratio/-x, release the thread's transform scratch (`zs_trim()`, or a
retention cap in `zs_free`: keep nothing above 1 MiB in those modes); balanced and speed keep the cache, whose point
is to avoid page faults on the fast path. (c) Optionally, a compact word table with the same iteration order
(a `uint32` slot index of 4 MiB plus entries only for the words seen, instead of 24 MiB zeroed per block): the
selection order `top[]` is the table order today, so the index array preserves it and the output stays identical;
kept only if identical on the whole corpus. (d) `rbuf`/`pos` buffers released after the block that needed them when
they exceed the next blocks' need.

**Files.** `src/core/blocks.c`, `src/core/memory.c`, `src/core/pool.c`, `src/transforms/word.c` (only for (c)),
`tests/`, `docs/MEMORY-MODEL.md`.

**Expected gain and basis.** Section 3.2: dickens ratio 103.4 -> about 62 to 70 MiB peak (bound measured with `-n`:
61.7); enwik8 ratio 663.6 MiB minus 24 to 95 MiB (3.2: the table is certain, the touched part of `tbuf` is
not separable before the change is built). Where the transform's output is used, releasing its scratch lowers
the coder stage only, and the peak then becomes the transform stage itself (figures are allocated bytes from the
maps of 3.2, arithmetic on them, not new measurements): Loghub at ratio 82.2 -> coder stage 45.4, transform stage
36.8 + 9.6 + 8.6 = 55.0, so about 55 (-33%); Loghub at `hc -l 9` 69.0 -> about 55 (-20%); dickens `hc -l 9` 75.9 ->
coder stage 51.9, transform stage 24.0 + 21.9 + 19.4 = 65.3, so about 65 (-14%), or about 52 (-31%) with the compact
word table of (c). On nci the peak is inside the log transform and (a), (b) do not lower it: that is claim #20. CPU: one
`word_encode` pass saved per text block at ratio and -x (size of the gain unknown until measured; the `-n` runs were
within noise).

**Risks.** Format: none intended; the danger is a path where the word-coded bytes are used after all (a block
planned as words that is not `looks_text` at ratio keeps LZMA2 over the word-coded bytes: the skip condition keeps
that case on the old path), guarded by the identical-frame test over the corpus plus the determinism suite. Speed:
`zs_trim` before the coder makes the next block's transform fault its scratch in again (24 MiB = about 6,000 page
faults per 16 to 128 MiB block: negligible beside zstd 19, Brotli, LZMA2 or a suffix sort; not applied to balanced
or speed). Memory: only down. Binary size: none.

**Success is measured by.** Identical SHA-256 against rc3 on the same matrix as 5.1; peak and average RSS per mode
on dickens, webster, enwik8, the Loghub file, nci, xml, silesia.tar; wall time per mode (3 runs, indicative) with the
ratio and -x text rows expected slightly faster; allocation maps before and after.

### 5.3 `log-transform-working-set` (claim #20, planned)

Replace the per-byte `uint32` arrays of `log_encode_m` (`toks` = 4 x (bytes + lines), `keys`, `tvar`, `tfl`,
`keys2`, the `nt x 1024` keep map and the seven per-line `uint32` arrays) by line-relative offsets, bit flags and
one arena sized from a first counting pass. Output identical. Design target, not a measurement: about 3 x block
instead of 8.6 x (Loghub) to 16.8 x (nci); the 4-byte-per-byte token index alone is 4 x. Risk: a subtle change of the template order would change bytes: the

1 and 4 threads and at hc/ratio.

### 5.3b `table-transform-working-set` (claim #50, planned)

`tbl2_encode` grows its output with `bput` (capacity doubled each time, the old block parked in the thread cache)
and `ncol_parse` allocates per-column arrays that are all live together (56 allocations for this table). Plan: one
counting pass that sizes the per-column buffers exactly, parse arrays reused column after column where the algorithm
allows, 8-byte value arrays narrowed where the range is known, one arena. Output identical (gate: identical frames on
the OWID table and on every table of the acceptance set). No gain is quoted before it is built: I have the
before-map only.

### 5.4 `kmem-enc-estimates-calibrated` (claim #21, planned)

A table per (codec, level, size class) fitted from allocation traces, a transform term per plan type, and an
on-line correction: the governor reads the process's own resident set next to its reservations and scales the
estimates of the codec class that is running (clamped, with the existing hysteresis). It decides only how many jobs
run, so bytes cannot change; the determinism check under forced budgets stays the gate. An allocation failure inside
a job is retried once when the job runs alone, instead of failing the call. Measured by: estimate / traced peak
between 1.0 and 1.3 on the corpus, jobs in flight under 512 MiB / 4 GiB budgets, and `-x -M 256M` encoding within
its cap.

### 5.5 `lib-idle-retention` (claim #22, planned)

At the end of a call, free per-thread buffers above about 4 MiB and codec contexts above a size cap; keep the small
contexts that make repeated small calls fast; add `kolmo_trim()`. Measured by `idle.c` (145,196 KiB today; target a few MiB)
and by a repeated-small-call timing to show the fast path did not slow down.
