Pipeline as it concerns this lens. A one-shot frame (`CZN1`) is a 32-byte header, a 16-byte index entry per block
(raw size, stored size, checksum, codec, flag), then the block payloads in order. Blocks are independent. The decoder
parses and CRC-checks header + index (`parse`), admits the frame against the memory limit (`frame_admit`, header byte
11), then pool workers take blocks, reserve their working set with the governor and decode them. Three decode
drivers exist: buffer to buffer (`kolmo_decompress`), seekable file to seekable file (`kolmo_decompress_file`: pread a
payload into `packed`, decode into `rbuf`, pwrite), and the stream decoder (`kolmo_stream_decompress_limited`), which
reads each `CZNS` frame whole into memory and range-decodes it in windows. The stream encoder
(`kolmo_stream_compress`) reads fixed segments (64 MiB by default) and calls the one-shot compressor on each.

| command | result |

| one byte flipped at offset 30,000,000 of the 71-block balanced frame, `kolmo -d` | `checksum mismatch`, exit 1, **no output file** (70 of 71 blocks are intact) |
| 1,000 random bytes appended to a frame, `kolmo -d` | decodes, output identical (trailing bytes are ignored, as for IDX1/DDP1) |

The README says the stream mode works on pipes. Compression does; **decompression from a pipe does not work at all**
through the CLI, for either format. zstd, xz, gzip and brotli all decode `cat x | tool -d` in bounded memory.

## 3. Gaps, ranked by expected gain

1. **Stream output is 10-12% larger than one-shot on archives** (tar; the same mechanism applies to any format
   `meta_segments` reads from headers). Rivals lose nothing when streaming. Measured recoverable gain: -10.48%
   balanced, -9.24% speed on silesia.tar. Claim #36, execute.
2. **No bounded-memory decode outside the seekable file path.** Stream decode 106 MiB vs 21 MiB at one thread; pipe
   decode impossible. Claim #37, execute.
3. **Range reads read everything**: 58-60 MiB RSS and the whole file's I/O for 4 KiB; not available on streams; a crash
   on a large length; `kolmo_archive_extract` re-parses and re-CRCs the index for every run of blocks. Claim #45,
   planned.
4. **No recovery from damage**: one byte loses the file although blocks are independent and individually checksummed.
   Claims #46 (salvage) and #47 (parity extension), planned.
5. **Compress from a pipe is an error unless `-s` is given.** Claim #49, planned.
6. **File decode path copies each byte twice more than needed and holds three frame-maximum buffers per worker.**
   21 MiB at one thread and 61-64 MiB at four for 4 MiB blocks. Gain not measured yet. Claim #48, planned.
7. Not claimed, noted for the owner: range-read latency in hc/ratio is one whole block (up to 128 MiB of BWT, LZMA2 or
   one-window zstd); finer granularity is a format question (restart points) with a ratio cost. The stream encoder's
   memory is the segment (110 MiB at balanced where `-S 4` needs 29.5 MiB): once #36 keeps the structure, smaller
   default segments may cost little ratio; I will measure `-S 4/8/16` with the new segmenter and report, without
   proposing a default.

## 4. Plan

### 4.1 czns-struct-segments (claim #36, execute, first)

Design. `kolmo_stream_compress` gains a structure-carrying mode (new entry `kolmo_stream_compress_opts` with a flags
field; CLI switch `--stream-struct`, default off):
- A tar walker in the stream reader: when the first segment starts a ustar archive, follow the member headers
  (512-byte header, octal size, padded data) across reads, with only the next header's absolute offset as state.
- Cut rule: a segment ends at the last member boundary that fits in the segment buffer; the bytes read past the cut are
  kept for the next segment. Segment length varies up to the `-S` size, so "one segment in memory" still holds.
- A member longer than the segment is cut at the segment size; the next segment then carries "first header at offset
  k". A new internal entry of `meta_segments` plans `[0, k)` as data and walks the tar from `k`. `mt_tar` also accepts
  a final member cut by the buffer end when the walker says so.
- The hook is generic (a structure state passed from one segment to the next) so zip/NPZ and concatenated files can
  follow under the same claim.

Format and compatibility. `CZNS` version 1 is unchanged: the rc3 decoder never reads `seg_bytes` as a bound and
already accepts frames of any length. I will verify every output with the **rc3 binary** as decoder. The bytes written
differ from rc3's `-s`, so the mode is opt-in. **A default switch is a proposal for the owner, to be flagged loudly
with the table below; I will not change the default.**

Files: `src/core/stream.c`, `src/plan/meta.c`, `src/core/compress.c` (internal hint parameter), `src/kolmo.h`,
`src/cli/cli.c`, tests, SPEC.md, README.

Expected gain and basis: -10.5% (balanced) and -9.2% (speed) on silesia.tar, from the emulation in 2.1 with the
unmodified binary; zero change on single-type streams (their plans do not depend on the cut).

Risks: a tar with unusual headers (base-256 sizes, sparse members) must make the walker give up and fall back to fixed
cuts, never mis-cut (a cut is always legal; only the ratio is at stake). Memory: one `memmove` of the carried tail per
segment. Speed: negligible (headers only). Binary size: under 1 KiB.

Success measure: sizes of `-s --stream-struct` vs `-s` vs one-shot at speed/balanced/hc/ratio on silesia.tar, a tar
with one member larger than the segment, a tar read from a pipe, and enwik8 (must be unchanged); each decoded by the
rc3 binary and compared by SHA-256; encode RSS and wall time (indicative).

### 4.2 stream-decode-incremental (claim #37, execute, second)

Design. A sequential frame reader used by both formats:
- Read the 32-byte header, then `nb x 16` bytes of index. The frame length is known (CZNS prefix) or computed from the
  index (plain CZN1 on a pipe: header + index + the sum of stored sizes, overflow-checked). `parse` and `frame_admit`
  run on the header + index buffer exactly as `kolmo_decompress_file` already does, so every existing check (CRC,
  sizes that add up, limits, declared memory) stays.
- Decode in windows of at most T consecutive blocks: read the window's payloads sequentially into one buffer, decode
  on the pool (the existing `decompress_worker`, with a base offset for payloads and for output so no intermediate
  `rbuf` copy is needed), write the window in order. Peak is about T x (payload + block + coder working set), whatever
  the segment or file size. Governor reservations are unchanged.
- Bytes after the last payload (IDX1, DDP1, parity) are skipped. Video frames (codec 20), dictionary and profile
  frames keep the whole-frame path, documented.
- API: `kolmo_decompress_fd(in_fd, out_fd, threads, limits)` for either magic on any descriptor;
  `kolmo_stream_decompress_limited` calls the same reader per frame. CLI: `-d` on a non-regular input or `-` takes it;
  the magic is sniffed from the same descriptor (fixes the 4 lost bytes).
- Second step if the wall time is behind rc3: read the next window while the current one decodes (two buffers).

No format change, no bytes change. Files: `src/core/stream.c`, `decode.c`, `io.c`, `src/api/api.c`, `src/kolmo.h`,
`src/cli/cli.c`, tests, SPEC.md, docs/MEMORY-MODEL.md, README.

Expected gain and basis: stream decode at the file path's memory (measured 21 MiB vs 106 MiB at one thread, 61-64 vs
138 MiB at four, for the same blocks), and pipe decode working where it fails today. I will not quote a figure for the
new code until it is measured.

Risks: a forged index on a pipe (sizes are validated against each other and against the limits before anything is
allocated; a payload shorter than declared is a clean `KOLMO_ERR_CORRUPT`); decode throughput with many tiny blocks
(windows are then grouped up to a byte budget); interaction with R06 #7 (dispatch order inside `run_decode`): my reader
is a separate driver that calls the same worker, so the two changes touch different functions of `decode.c`.

Success measure: SHA-256 of the output equal to rc3's decode for all six modes on Silesia members and for `.czs`
files written by the rc3 binary; truncated, corrupt and forged inputs under ASan; `-M` and decode limits honoured;
peak and average RSS and wall time against rc3 at `-T 1` and `-T 4`, and against `xz -d` on a pipe.
