## 2. How threads are used in rc3 (facts from the code)

1. **One level of block parallelism.** `run_pool(fn, J, threads, units)` (`core/pool.c`) wakes `min(threads, units) - 1`
   persistent workers; each worker pulls the next block **in input order** from `atomic_fetch_add(&J->next, 1)`
   (`compress_worker`, `decompress_worker`). Compressed blocks are written in input order: a block that finishes early
   is copied (`malloc` + `memcpy`, `emit_block`) and waits in `J->out[]`, with no bound on what is buffered.
2. **Inner threads are a static quotient.** `J.fqthreads = threads / min(nb, 256)` (at least 1), fixed for the call
   (`core/compress.c:176`, `core/decode.c:336`). It is what the BWT stages (LZP, suffix sort crew, QLFC, inverse BWT),
   the codec-25 parts, the -x trials, the CM preset race, the FASTQ and GR6 coders receive as `codec_ctx.threads`.
   Consequences: with `nb > threads / 2` every block is single-threaded for its whole life, also when it is the last
   block running and every other core is idle; with `nb < threads` the remainder `threads % nb` is never used.
3. **Inner regions start their own threads.** `kolmo_par_for` creates and joins pthreads per call; the suffix sorter
   creates a `kolmo_crew` per sort whose idle workers spin (`SPIN_LIMIT` 20000 pause loops, `BARRIER_SPINS` 4000 per
   barrier) before sleeping; `xtrial_start`, `cmp_run`, `cm_compress_raced`, `ultra_keep_transform`, `fs_worker`,
   `kf_tp_worker`, `ka_run_pool` each call `pthread_create` directly. None of them knows how many cores are free.
4. **Optional work decides once.** A trial or part that does not get its memory reservation at the moment it asks
   (`kmem_try_reserve`) runs later inline on the owner thread and is never picked up by a thread that becomes free.
5. **Planning.** Members/segments are planned on the pool (`plan_worker`), one thread per plan when there are several
   segments; a single-segment file is planned on one thread (only table formula discovery uses `threads`).
6. **Single-stream coders.** LZMA2 (codec 6, vendored liblzma subset, built without threads), zstd at hc (one call per
   block; hc text uses one 128 MiB block), Brotli, context mixing on text: one thread per block whatever `-T` is.
7. **Bytes never depend on -T** (checked again below: the instrumented `-T 1` frames equal the rc3 `-T 4` frames in
   every mode measured).

## 6. Plan for the two points I will implement tonight

### 6.1 #7 sched-cost-order-elastic (primary; execution only, same bytes for every -T)

Design:
1. **Cost-ordered dispatch.** Before `run_pool`, build `order[nb]`: blocks sorted by estimated cost, descending,
   ties by index. Cost = `len` x a per-class weight taken from the block's plan and the mode's codec (LZMA2 binary,
   zstd level, BWT, CM, stored/packed), the weights fitted from the logs of section 3.1 (they only order work; a
   wrong weight costs time, never bytes). Workers take `order[next++]`. Decode: cost = raw size x codec weight from the
   index entry; output goes to fixed offsets, so nothing else changes.
2. **Bounded reorder buffer (compress).** `emit_block` keeps finished out-of-order payloads; with longest-first the
   early blocks finish last, so the buffer would grow. Rule: when the buffered bytes exceed a cap (default 64 MiB or
   2 slots, whichever is larger) the next pick is the lowest unfinished index (input order), which advances the
   write head; below the cap, longest-first. Peak buffered bytes are reported by a test hook.
3. **Elastic inner budget.** A per-call counter of free threads: `spare = threads - running block workers`. A
   worker that finds no block left does not exit: it helps. Inner regions publish their task loops in a small
   registry (`kolmo_par_for` gains a registered form: fn, ctx, ntasks, shared atomic cursor); helpers and late
   joiners run tasks from registered loops until the run ends. `kolmo_par_for`'s contract (each task writes only its
   own output, tasks handed out from one counter) already makes the result independent of who runs a task. Regions
   that cannot be joined late (the suffix-sort crew, `xtrial_start`, the preset race) size themselves from
   `spare` at the moment they start instead of from the constant `fqthreads`, and return what they took.
   `J.fqthreads` remains as the upper bound where a count reaches a format decision (none found; the tests check).
4. Interface shaped as `take(n) / give(n)` so the w4-multi token hooks can back it later.

Files: `src/core/pool.c`, `src/core/blocks.c`, `src/core/compress.c`, `src/core/decode.c`, `src/core/trials.c`,
`src/algo/par.c|h`, `src/codecs/cm_par.c`, `src/codecs/cm.c`, `tests/`, `docs/`.

Expected gain and basis: section 3.1 (order alone: hc T=8 -31%, T=10 -17%, T=4 -9%; ratio decode T=4 -27%; eco decode
T=10 0.13 → 0.10 s). The budget adds what the simulator cannot show: BWT blocks at the tail get the freed cores
(webster's inverse BWT is the 2.16 s that bounds ratio decode at every T), and #6's chunks are run by helpers.

Risks: format none (execution only; identical-frame tests for T = 1..8 in all six modes on silesia.tar, enwik8 and the
unit corpora, plus the existing determinism suite); memory: reorder buffer bounded by the cap, helpers reserve with the

lines; deadlock: helpers never wait on a lock while holding a reservation (same rule as `docs/MEMORY-MODEL.md`).

Success measure: (1) frames byte-identical to rc3 for every mode and T; (2) with per-block CPU logged, the measured
start order equals the planned order and the simulated makespan from the new schedule equals `longest` of section
3.1; (3) wall time under `tools/measure.py` at T=4 for hc/ratio/eco compress and decompress on silesia.tar, labelled
indicative; (4) whole-process CPU not higher than rc3 at the same T; (5) final speeds on the owner's M5.

### 6.2 #6 lzma2-overlap-chunks-mt (second; opt-in, bytes differ from rc3's single stream, rc3 decodes them)

Design: `lzma_compress` cuts the block into chunks of C bytes (a rule of the data only: n and the opt-in parameter,
never -T). Chunk k is coded by `lzma_raw_buffer_encode` with `preset_dict` = the W bytes before it, which makes the
LZMA2 encoder start the chunk with "state reset, new properties, no dictionary reset" (control byte 0xC0 class;
observed 0xc2 in the harness). The chunks' packets are concatenated, inner end markers (the final 0x00) dropped, one
end marker kept. The result is one standard LZMA2 stream: the unchanged rc3 codec-6 decoder reads it (feasibility
shown in section 9 with the same decode call rc3 makes). Chunks are tasks of a registered loop (6.1), so they run on
`fqthreads` when the block is alone and on helpers otherwise. Each chunk's encoder uses a dictionary of the next power
of two above W + C (not the stream's 64 MiB), so T chunk encoders need about what one 64 MiB encoder needs.
Opt-in: a new `transforms` bit (`KOLMO_T_LZMA_CHUNKS`) and CLI `--lzma-chunks[=MiB]`; default unchanged.

Files: `src/codecs/lzma.c`, `src/core/blocks.c` (passes the opt-in and the governor context), `src/core/compress.c`,
`src/core/memneed.c` (per-chunk encoder estimate), `src/kolmo.h`, `src/cli/cli.c`, `tests/`, `SPEC.md` (a note: codec
6 payloads may contain mid-stream state resets; nothing new for a decoder), `docs/`.

Expected gain and basis: section 3.1 (ratio capped at 2.05x by one LZMA2 block) and the measured size and CPU cost of
C and W in section 9.

Risks: format: none for decoders (same codec id, standard stream; rule 3 respected by the opt-in); size: lost matches
beyond W and one state reset per chunk (measured in section 9); CPU: the match finder is primed over W bytes per
chunk (measured); memory: per-chunk encoders reserved with the governor (optional helpers only try); **rule 2**: the
coder is the vendored liblzma that codec 6 already is. The mechanism added (cut rule, overlap, splice, scheduling) is
Kolmo code and no library or compressor is added, but the owner should confirm that speeding up a vendored coder is
within the originality rule; if not, the same design moves to Kolmo's own KLZMA (`klzma-chunked-mt`, planned, new
codec id) and #6 stays an opt-in measurement.

Success measure: sizes vs rc3 per file (exact), round trip by the **rc3 binary's** decoder (not the patched one),
identical frames for T = 1..8 with the option on, per-chunk CPU and simulated makespan, indicative wall at T=4,
corrupt-input test unchanged (decoder untouched).

  waits were short and the budget of 6.1 says a core is free), crew size from the block size, fewer wake-ups; bytes
  unchanged. Success: BWT block CPU at T=4 within 1.3x of T=1 (now 2.8-3.0x) at equal or better wall on an idle
  machine, and no slowdown versus T=1 on a loaded one.
- **cm-primed-parts-mt** (E): codec 25 version 1: parts whose models are primed on a shared prefix so text can be
  cut; decode in parallel after the prefix is decoded. Measure first (proxy in section 9), no default change.
- **zstd-overlap-chunks-mt** (F): hc one-window blocks coded as overlapped jobs in one zstd frame; conditional on the
  owner's rule-2 ruling (the mechanism would be zstd's own job splitter or a Kolmo splice needing a decoder change).
- **plan-phase-parallel** (G): the independent probes of `make_plan` (image, record, float/int/img8 graph, text/table)
  as tasks of a registered loop; the choice rule reads their results in today's order, so plans are unchanged.
- **asym-core-dispatch** (H): on macOS set the QoS of the worker that takes the costliest unsplittable block to
  user-initiated and the others to utility (and Linux: prefer P-cores via `sched_setaffinity` from the cpu capacity
  files) only when blocks are unbalanced; measure on the M5 at T=10 (hc/ratio/-x one-big-block inputs); bytes unchanged.
- **klzma-chunked-mt** (I): chunked framing for Kolmo's own KLZMA with an overlap window (new codec id, opt-in), so the
  native LZMA-class coder scales with threads the way #6 does.

## 8. Things I looked at and do not propose

- Speed/balanced block phase: at the bound already (3.1); the thread pool itself (condition-variable wake-up, one
  generation counter) costs nothing measurable at these block sizes.
- Speed-tier decompression is half kernel time (`pwrite` of decoded blocks); an `mmap`ed output would trade the copy
  for page faults of the same order. Not claimed; no measurement supports a gain.
- Splitting BWT blocks for threads: R03's #33 goes the other way (larger blocks are 5-9% smaller); the inner stages
  already have data-defined parts.
