How images are coded today:

| level | 8-bit | 16-bit |
|---|---|---|
| balanced..hc | graph node IMG8: LOCO-I median residual per byte (neighbour `step` bytes left, row above), zigzag, leaves by zstd / Huffman / rANS | `T_IMG`: left / average / median residual of 16-bit samples, lo plane then hi plane, zstd |
| ratio | same node, leaves by LZMA2 and by block sorting, smaller kept | same transform, BWT or LZMA2 |
| -x | both of the above **and** codec 17: context mixing over the raw pixel bytes, 20 hashed neighbour contexts, 4 mixers, 3 APMs; smallest kept | same transform + general CM (no image model: tracker D3 "not done") |

Geometry: from a header (`meta_image8`: NPY u1, PGM/PPM maxval < 256, PAM, BMP, baseline TIFF) or, without one,
from a lag search over **36 fixed widths x {1,3,4} channels** (`kg_img8_trial`, `WS[]`).

Findings from the code:

1. **No colour decorrelation anywhere.** IMG8 predicts each byte from the same channel of its neighbours; the
   inter-channel redundancy is left to the leaf coder. Codec 17 sees the raw R, G, B bytes; its only inter-channel
   contexts are `icp = W + P1 - W1` and `icn = N + P1 - N1` (the colour difference of ONE neighbour), so in the
   colour-difference domain it has a left / up predictor but no gradient, no median, no two-neighbour context.
2. **Codec 17 has no prediction-error feedback**: no context built from how well the predictors did on the
   neighbouring pixels (CALIC's error energy, JPEG XL's weighted-predictor error property), no blended predictor,
   and the "activity" selector uses three gradient magnitudes only.
3. **Headerless images need one of 36 widths.** Any other width (451, 371, 1411, 427...) is not an image for Kolmo.
4. **16-bit**: one channel only (`img_plan_t` has no channel count), stride from a search, no header geometry, no
   image model at `-x`, no notion of stacked slices.
5. Parsers (`meta_image8`, `kg_img8_inv`, `cm_decompress_img`): I checked the bounds arithmetic of each header
   reader and decoder parameter check and found no overflow or out-of-bounds read to report.
6. Free format space I will use: graph node ids above 7 (`KG_MAXOP = 7`; an unknown node id fails cleanly), and
   bits 3-6 of codec 17's channel byte (`ich = in[8] & 0x7f; ... ich > 4 -> return -1`: an rc3 decoder refuses a
   stream with any of them set).

## 4. Plan

### 4.1 `img8-colour-node` (execute, first)

- **Design.** New graph node **8, IMG8C**: params `row bytes uv | channel step u8 (3 or 4) | head uv | colour mode u8`.
  Colour mode: bits 0-1 the reference channel index r, bits 2-3 the map: 1 = every other colour channel minus the
  reference, plus 128 (subtract-green when r = 1; also right for BGR); 2 = chain in byte order (c0, c1-c0+128,
  c2-c1+128). A fourth channel (alpha) is left alone. All arithmetic mod 256, so the inverse is exact for any
  bytes. Forward: map a copy, then the existing median kernel (`KOLMO_K->med8_fwd`); inverse: `med8_inv`, then the
  inverse map in place. The SSE/AVX2/NEON median kernels are reused untouched; the map itself is a branch-free
  loop over pixels (scalar tonight; explicit SIMD later under the same claim if the M5 shows a need).
  Outputs are the same two streams as IMG8 (residuals, rest), so every leaf coder — including R02's leaf 33 with
  its lag contexts — applies unchanged.
- **Choice.** `kg_img8_trial` scores plain IMG8 and the two maps with the trial it already runs (zstd on the trial
  slice, 32 KiB screen first) when the step is 3 or 4, and keeps the smallest; the plan carries the mode in a new
  `plan_t` field (and `plan/profile.c`, which serialises plans, must learn it or leave such plans out). color.ppm shows why a
  fixed choice would be wrong.
- **Files.** `src/transforms/graph.c` (node, inverse, `kg_decode` case, `KG_MAXOP`), `src/algo/predict.c` (map
  kernels), `src/plan/planner.c`, `src/plan/plan.h` / `profile.c` (plan field), `src/core/blocks.c` (calls),
  `SPEC.md` (node table), `tests/` (round trip incl. random bytes and all modes, damaged parameters), fuzz seed.
- **Compatibility.** rc3 frames are untouched (their nodes are 1-7). A frame with node 8 is refused cleanly by rc3
  ("unknown node id"). Because it changes the bytes written for RGB images, **it ships behind an option first**
  (`--img-colour` / `KOLMO_IMG_COLOUR=1`, final name with the owner); I will report the measured table and flag
  loudly that the proposal is to make it the default for RGB images at balanced..ratio.
- **Expected gain and basis.** Section 2.2: -12.5% / -8.4% / -6.7% on the 9 RGB files (balanced / hc / ratio), exact
  proxy. No change on grey images or non-images (the mode is only tried at step 3 or 4).
- **Risks.** Speed: one more pass over the pixels each way (decode of `balanced` images is recorded at ~1.2 GB/s on
  the M5; I expect a few percent, to be measured with `measure.py` here and labelled indicative); planner time:
  three trials instead of one on RGB candidates (bounded by the existing screen). Memory: one block-sized scratch
  in the encoder (the decoder maps in place). Binary size: under 1 KB. Format: one new node id.
- **Success.** (1) Sizes on the 17 files at balanced, hc, ratio equal the proxy within the parameter byte, every
  file round-trips (cmp), no file larger than rc3; (2) byte-identical output to rc3 with the option off on the 17
  images, the Silesia files and enwik8_10m (SHA-256); (3) `make check` and the new test pass, ASan clean; (4)
  indicative encode/decode time against rc3 on retina.ppm and astronaut.ppm.

### 4.2 `cmi-rev2-chroma` (execute, second)

- **Design, step 1 (the measured part).** Codec 17 revision 2: bits 3-4 of the channel byte carry the colour mode
  of 4.1 (0 = rc3's stream, bit for bit). The coder maps the pixel bytes after `ih` into a scratch buffer and runs
  the existing model on it; the decoder decodes into the output buffer and applies the inverse map in place at the
  end. The mode is chosen per block without running the model three times: by the planner's trial result when it
  comes from 4.1, else by the activity-conditioned entropy of median residuals (the statistic of `ent.py`: on the six files
  of the table in 2.2 it separates "map" from "no map" correctly, color.ppm included; between sg and ch it picks
  the larger one once, on astronaut, where the two differ by 0.2%). `-x -l 2` may code all modes and keep
  the smallest.
- **Step 2 (new contexts, each kept only if it pays on the 17 files).** Revision bit 5 selects a second context
  set using the 9 model slots that model 3 has and the image branch leaves empty (`CM_NMX` 21 -> up to `CM_NM3` 30):
  (a) error-feedback: the summed magnitudes of the median-prediction errors at W, N, NW, NE (kept in two row
  buffers) quantised to 16 classes, as a context with the prediction and as a mixer selector in place of the 3-gradient
  activity; (b) a blended predictor: four sub-predictors (W, N, gradient, N+NE-NNE) weighted by their recent
  local absolute errors, integer arithmetic only (encoder and decoder must agree bit for bit on every CPU), used as
  context alone, with the error class, and as the selector of the order-1 direct table and the APMs; (c) the residual
  of the earlier channel at this pixel as a context for the later channels (texture shared between channels).
  The idea of weighting sub-predictors by their local errors is the one published for CALIC (Wu & Memon,
  "Context-based, adaptive, lossless image coding") and JPEG XL's weighted predictor (Alakuijala et al., "JPEG XL
  next-generation image compression architecture and coding tools"); the code will be written from scratch for
  Kolmo's bitwise mixer, nothing is copied or linked.
- **Files.** `src/codecs/cm.c` (image branch only, new revision under its own compile-time loop so models 1-3 and
  rc3's image loop keep their code), `src/codecs/cm_image.c` (header bits, map, memory), `src/core/blocks.c` (mode
  from the plan), `src/core/memneed.c`, `SPEC.md`, `tests/test_cmimg.c`.
- **Compatibility.** Revision 0 streams decode exactly as before (same loop). A stream with any of bits 3-6 set is
  refused by rc3 (`ich > 4`). Default: behind `-x -l 2` or an option tonight; the report will propose the default
  switch for `-x` with the table, loudly.
- **Expected gain and basis.** Step 1: -11.7% on the 9 RGB files (2.2, measured proxy), from -1.2% to -12.8%
  against JPEG XL e9; grey unchanged. Step 2: unmeasured; the target is the 8 grey files (today +1.0% against e9)
  and the two synthetic RGB files (color +11.3%).
- **Risks.** Encode time: the mode statistic is one cheap pass; step 2 adds up to 9 model slots, so `-x` on images
  gets slower in proportion (to be measured, indicative); memory: +9 hashed tables at the image block's size class
  (`cm_mem_for`), declared in `memneed`. Step 2 may not pay: then it is recorded as a negative result and only
  step 1 ships. w4-cm (unmerged) edits the same function; I keep my change inside the `img` branches and a new
  revision loop to keep the merge mechanical.
- **Success.** `-x` total on the 17 files below rc3's 4,157,899 by at least the step-1 proxy (398,630 bytes on
  RGB), no file larger than rc3 (the smaller of revisions is kept), every file round-trips, rc3-written codec 17
  frames (the 17 files coded again with the read-only rc3 binary at `-x`) decode identically with the new binary; `make check-cmimg`
  under ASan with damaged revision bits.

### 4.3 Planned (owned by R05, not built tonight)
