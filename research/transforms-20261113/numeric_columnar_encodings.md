# Lightweight numeric and columnar encodings as stackable transforms (for kolmo)

Scope note: kolmo already has shuffle/transpose, delta, delta2, zigzag, gcd division, FOR, byte-plane split, an ALP-style decimal node, float sign/exponent/mantissa planes, an 8-bit gradient predictor, fixed-record detection, and has dropped Gorilla XOR, Rice, bit-packing and patched bit-packing. Those are not re-explained. All numbers below are quoted from the linked source; "Inferences" are mine. Two pages could not be fetched (permission prompt timed out): `arxiv.org/abs/2502.06112` (the pcodec abstract page; the HTML v2 of the same paper was fetched instead) and `github.com/pcodec/pcodec/blob/main/docs/format.md` (pco format spec, not read).

## 1. What do the 2022-2026 float schemes do differently, and which report gains when a general-purpose compressor follows?

### Takeaway
Across the papers' own tables, a general-purpose compressor alone (zstd, xz) matches or beats the whole XOR family (Gorilla, Chimp, Chimp128, Patas) and is only beaten by the decimal-aware schemes (ALP, Elf*, pco) on decimal-origin data; on genuinely full-precision doubles nothing gets much past about 1.2x. The only schemes that report evidence of stacking with a back-end coder are ALP (with RLE/dictionary cascades), pco (its own binning + tANS), byte/bit shuffle + delta filters, and byte-position clustering (TDT); none of the XOR/erasure papers test their output followed by zstd.

### Cited Findings

ALP / ALP-RD (SIGMOD 2024)
- ALP: per vector of 1024 values one exponent e and factor f; double encoded as round(n x 10^e x 10^-f), integers then go to FFOR (fused FOR + bit-packing). Values that do not round-trip are exceptions costing about 80 bits each (64-bit value + 16-bit position). Two-level sampling: 8 vectors per row group x 32 values to keep up to 5 (e,f) candidates, then 32 values per vector to choose among them. — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf)
- ALP-RD (real doubles): per row group a cut position p (at least 48) splits each double; the right p bits are bit-packed raw, the left front bits are dictionary-coded with up to 8 entries plus 16-bit exceptions when exception rate is at most 10%. — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf)
- Average bits per value across all datasets: Gorilla 42.2, Chimp 37.7, Chimp128 28.7, Patas 35.5, PDE 31.4, Elf 23.1, ALP 21.7, LWC+ALP 18.8, Zstd 20.6. Time series only: ALP 16.4, LWC+ALP 13.2, Zstd 17.2. Non time series: ALP 25.7, LWC+ALP 23.1, Zstd 23.3. — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf)
- So plain zstd (20.6) beats plain ALP (21.7) on the all-dataset average in ALP's own table; ALP only passes zstd once cascaded with dictionary or RLE ("LWC+ALP", 18.8). Per-dataset examples (bits/value, ALP / LWC+ALP / Zstd): Air-Pressure 16.5 / 11.9 / 8.7; City-Temp 10.7 / 10.0 / 16.2; Stocks-USA 7.9 / 7.9 / 7.8; NYC/29 40.4 / 24.7 / 20.5; CMS/9 11.7 / 11.3 / 14.7. — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf)
- ALP-RD is the path used on POI-lat and POI-lon: 55.5 and 56.4 bits/value versus Zstd 48.1 and 53.1; the paper says ALP-RD achieves at most about 1.2x and is roughly 3x slower to compress and 4x slower to decompress than ALP. — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf)
- Speed, tuples per CPU cycle (compress / decompress): ALP 0.487 / 2.609; Chimp 0.042 / 0.039; Chimp128 0.040 / 0.040; Elf 0.010 / 0.012; Gorilla 0.052 / 0.047; PDE 0.002 / 0.387; Patas 0.060 / 0.157; Zstd 0.035 / 0.101. — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf)
- float32 ML model weights (average of four models, bits/value): ALP-RD32 28.1, Zstd 29.7, Chimp and Chimp128 33.4, Gorilla 34.1, Patas 45.6; about a 12% reduction, described as the only float encoding in that test to compress at all. — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf)
- The ALP repository README describes the two paths the same way: decimals multiplied by a power of ten then FastLanes FOR; high-precision values have only the left part dictionary-compressed and the right part stored uncompressed "because it is often highly random". — [cwida/ALP](https://github.com/cwida/ALP)

Pseudodecimal (BtrBlocks, SIGMOD 2023)
- PDE splits each double into signed significant digits (max 32 bits) and a base-10 exponent (5 bits), trying exponents 0 to 22 and requiring exact round trip; failures (-0.0, Inf, NaN, tiny values) take exponent code 23 and are patched. It is disabled when more than 50% are exceptions or fewer than 10% of values are unique (dictionary is then better). — [BtrBlocks paper](https://www.cs.cit.tum.de:443/fileadmin/w00cfj/dis/papers/btrblocks.pdf)
- PDE compression ratio vs FPC / Gorilla / Chimp / Chimp128 on Public BI double columns: CommonGov/26 75.0 vs 15.1 / 48.0 / 28.0 / 6.9; CommonGov/31 23.4 vs 9.3 / 14.3 / 13.3 / 5.6; CMSProvider/9 6.6 vs 2.7 / 2.3 / 3.4 / 2.4; NYC/29 (high precision) 1.0 vs 1.5 / 2.1 / 2.5 / 1.7. PDE wins 7 of 12 columns and loses on high-precision columns and on columns with long runs or few uniques. — [BtrBlocks paper](https://www.cs.cit.tum.de:443/fileadmin/w00cfj/dis/papers/btrblocks.pdf)
- ALP's table puts PDE at 31.4 bits/value on average versus ALP 21.7, and PDE compression at 0.002 tuples/cycle (ALP is reported 251x faster). — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf)

Elf / Elf+ / Elf* / SElf*
- Elf zeroes ("erases") the low mantissa bits that are not needed given the value's decimal place count alpha, so XOR with the previous value has long trailing-zero runs; erased bit count is 52 - (ceil(alpha x log2 10) + floor(log2 |v|)); restore adds back using the known alpha. Elf+ improves the coding of significand counts (values in a series tend to share one). Elf* (batch) replaces the fixed leading-zero code with rules found by dynamic programming and codes trailing zeros; SElf* does the same over a sliding 1,000-value window for streams. — [Adaptive Encoding Strategies for Erasing-Based Lossless FP Compression](https://arxiv.org/pdf/2308.11915)
- Compressed size as a fraction of original (lower is better), time series / non time series: Gorilla 0.768 / 0.883; Chimp 0.697 / 0.793; Chimp128 0.420 / 0.629; Elf 0.375 / 0.551; Elf+ 0.331 / 0.525; SElf* 0.297 / 0.484; Elf* 0.287 / 0.480; Xz 0.331 / 0.514; Zstd 0.406 / 0.568; Snappy 0.514 / 0.664. — [Adaptive Encoding Strategies paper](https://arxiv.org/pdf/2308.11915)
- In that table Zstd (0.406) already beats Chimp128 (0.420) on time series and Xz (0.331) ties Elf+; only Elf*/SElf* beat Xz, by about 13.3% (time series) and 6.6% (non time series). — [Adaptive Encoding Strategies paper](https://arxiv.org/pdf/2308.11915)
- Time per block in microseconds (compress / decompress, time series): Gorilla 22 / 21; Chimp 27 / 25; Chimp128 33 / 25; Elf 78 / 52; Elf+ 65 / 44; SElf* 69 / 34; Elf* 79 / 34; Zstd 216 / 44; Xz 1566 / 273. The paper does not evaluate Elf output followed by a general-purpose compressor. — [Adaptive Encoding Strategies paper](https://arxiv.org/pdf/2308.11915)

DeXOR (arXiv Jan 2026) and its description of Camel / Chimp
- DeXOR does an "XOR in decimal space": it strips the longest common decimal prefix shared with the previous value and stores the remaining decimal suffix as a scaled integer (88.1479 after 88.1537 leaves suffix 479), with a 2-bit control code to reuse the previous prefix/tail coordinates, and an exception path (exponent difference coded adaptively) for high-precision values. — [DeXOR paper](https://arxiv.org/html/2601.00695v1)
- Reported geomean average compressed bits per value: DeXOR 17.82, Elf+ 27.31, Chimp128 31.37, Gorilla 49.09; on low-decimal-place data DeXOR 12.70, Camel 14.86, Elf+ 20.57, Elf 23.18. Speed (MB/s, geomean) DeXOR 14.94 compress / 53.12 decompress. Headline claim: about 15% better ratio and about 20% faster decompression than the best competitors. — [DeXOR paper](https://arxiv.org/html/2601.00695v1)
- Source inconsistency: the same paper's table lists SElf* at 14.54 bits, lower than DeXOR's 17.82, while the text ranks DeXOR second only to Elf*; the extracted per-dataset tables were partly garbled, so treat the ranking against SElf*/Elf* as unresolved. — [DeXOR paper](https://arxiv.org/html/2601.00695v1)
- DeXOR's characterisation of competitors: Chimp128 adds a 128-value sliding window to choose the XOR reference; Camel splits a decimal into integer and fractional parts and exploits smoothness in the integer part, and "fails on high-precision data"; ALP works on 1024-value mini-batches. It also states that stacking LZ4 or Snappy on IoTDB's existing encodings adds under 2% space reduction. — [DeXOR paper](https://arxiv.org/html/2601.00695v1)

FCBench (cross-domain benchmark, 33 real float datasets, single and double precision)
- Overall compression ratio by method: bitshuffle+zstd 1.466 (best), bitshuffle+LZ4 1.430, fpzip 1.329, MPC 1.322, Chimp 1.309, nvCOMP LZ4 1.296, SPDP 1.256, ndzip-CPU 1.219, pFPC 1.154, Gorilla 1.116, BUFF 0.984. By domain: fpzip best on HPC (1.601), bitshuffle+zstd best on observation data (1.697), Chimp best on database data (1.382), nvCOMP LZ4 best on time series (1.603). — [FCBench](https://arxiv.org/html/2312.10301v2)
- Median ratio over all measurements is 1.16; medians by precision 1.225 (single) and 1.202 (double); database-domain median is only 1.080. Family medians: dictionary-based 1.309, Lorenzo-based 1.219, delta-based 1.116. The authors say there is "no clear winner" statistically. — [FCBench](https://arxiv.org/html/2312.10301v2)
- Throughput GB/s (compress / decompress): ndzip-CPU 2.192 / 1.636; bitshuffle+zstd 1.407 / 1.328; bitshuffle+LZ4 0.923 / 1.181; pFPC 0.564 / 0.351; BUFF 0.202 / 0.254; SPDP 0.181 / 0.178; fpzip 0.079 / 0.074; Gorilla 0.047 / 0.146; Chimp 0.034 / 0.175. — [FCBench](https://arxiv.org/html/2312.10301v2)
- Supplying true array dimensions versus treating data as 1-D made no significant difference to ratio (fpzip 1.334 vs 1.326; ndzip-CPU 1.223 vs 1.210; MPC 1.347 vs 1.365; Mann-Whitney p from 0.69 to 0.96). — [FCBench](https://arxiv.org/html/2312.10301v2)
- Block size barely moves ratio: bitshuffle+zstd 1.463 at 4K, 1.466 at 64K, 1.491 at 8M blocks; Chimp 1.309 / 1.315 / 1.315. — [FCBench](https://arxiv.org/html/2312.10301v2)
- BUFF had a weak overall ratio (0.984, and 0.780 on observation data) and a memory footprint about 7x its input. FCBench's recommendation for general CPU use is bitshuffle+zstd. — [FCBench](https://arxiv.org/html/2312.10301v2)

Typed Data Transformation (TDT, 2025): byte-position clustering before a generic compressor
- TDT computes per-byte-position entropy features and a 256-bin histogram, hierarchically clusters the byte positions, and emits each cluster as its own contiguous stream (a data-driven generalisation of byte shuffle where similar byte planes are kept together), after blocking to between L1 and L2 cache size. — [Floating-Point Data Transformation for Lossless Compression](https://arxiv.org/pdf/2506.18062v2)
- Reported gains: geomean ratio improvement 1.04x to 1.20x across back-ends; 1.24x over bitshuffle (both with zstd); by precision float64 1.075x, float32 1.19x, float16 1.08x. — [TDT paper](https://arxiv.org/pdf/2506.18062v2)
- float64 examples with zstd (TDT / plain zstd ratio): num-brain 1.265 / 1.065; astro-pt 1.366 / 1.047; msg-bt 1.383 / 1.126; num-control 1.146 / 1.058; tpch-order 2.091 / 1.836; wesad-chest 3.305 / 3.349 (a loss). With bzip2 (a BWT coder) TDT loses on the tpcxBB columns (2.170 vs 3.130, 2.110 vs 2.960). — [TDT paper](https://arxiv.org/pdf/2506.18062v2)
- Source inconsistency: the paper states several different aggregate figures (1.16x in the abstract, 1.04 to 1.20x and 1.04 to 1.17x elsewhere) and claims consistent improvement although its own table shows losses. Decompression throughput is reported 3.09x better overall (geomean), compression 0.96x. — [TDT paper](https://arxiv.org/pdf/2506.18062v2)

### Inferences
- kolmo's decision to drop Gorilla XOR is consistent with the literature's own numbers: zstd alone beats Gorilla, Chimp, Chimp128 and Patas on average in both the ALP and Elf tables. Chimp128 and Patas look like poor candidates for the same reason; I would not spend time on them.
- The transferable idea from Elf is not its bit-level coder but the erasure step as a pre-transform: for decimal-origin doubles that the ALP-style node rejects (too many digits to fit an integer, mixed precision), zeroing the redundant low mantissa bits and keeping a small per-value or per-block decimal-place count makes the low byte planes constant. This composes with byte planes and any entropy leaf. No paper measures Elf-erasure followed by zstd/BWT, so the gain is unverified; it is worth an isolated experiment.
- The ALP table shows the ordering "decimal-to-int, then dictionary/RLE cascade" matters more than the decimal step alone (21.7 to 18.8 bits). kolmo should check that its decimal node output can be fed to tokenize/dictionary and RLE nodes and not only to FOR/byte planes.
- ALP-RD's design (dictionary of at most 8 values on the top 16 or so bits, raw tail) is essentially what kolmo's sign/exponent/mantissa plane handling plus an entropy leaf already achieves; ALP-RD lost to plain zstd on both POI columns, so it is unlikely to add anything over existing planes plus zstd.
- TDT's result suggests a cheap variant worth testing: instead of one stream per byte plane, pick the grouping of byte planes per block (for example merge the top two planes, or merge the noisy low planes into one stored stream) by measured entropy. Reported gains are in the 4 to 20% range over plain compressors and its losses on bzip2 suggest it helps LZ leaves more than BWT leaves.
- Implementation cost (my estimate): Elf-style erasure about 150 to 300 lines of C plus a decimal-place detector that the ALP node already contains; byte-plane grouping about 100 lines on top of existing plane split; DeXOR-style decimal prefix removal is larger and overlaps the decimal node.

### Gaps
- Falcon, Camel (primary paper), SElf (primary paper), BUFF (primary paper), FPC, SPDP, ndzip and fpzip primary sources were not fetched this session. What I can say from prior knowledge, unverified here: FPC predicts each double with two hash-table predictors (FCM, DFCM) and codes the leading-zero-byte count of the XOR residual; fpzip uses a Lorenzo predictor over n-D grids and range-codes the residual; SPDP is a synthesized pipeline of byte-level stride-delta transforms feeding an LZ77 variant; ndzip uses an integer Lorenzo transform on hypercube blocks followed by a bit transpose and zero-word removal; BUFF splits decimals into integer and fractional byte-aligned sub-columns; Falcon is a GPU-oriented decimal-to-integer scheme. None of these statements is sourced in these notes.
- No source found that measures Chimp/Elf/Patas output followed by zstd or BWT. The only stacking evidence for that family is DeXOR's remark that LZ4/Snappy on IoTDB encodings adds under 2%.
- The ALP repository's benchmark chart is an image and could not be read; numbers above come from the paper PDF only.

## 2. Integers and timestamps: which cheap transforms beyond delta/FOR/zigzag/gcd have measured gains?

### Takeaway
The measured wins not already in kolmo are: number-level lookback (LZ at value granularity), higher-order consecutive deltas chosen by trial up to order 7, cross-vector RLE, dictionary plus cascades, byte-delta inside shuffled planes, linear and piecewise-linear model residuals (LeCo), and cross-column schemes (diff against a reference column, equality, one-to-one map, per-key FOR), which report column-level savings from a few percent to 85% and table-level gains of about 8 to 20%.

### Cited Findings

Byte shuffle vs bitshuffle vs shuffle + byte delta
- Blosc2 "bytedelta": after shuffle, take the byte-wise difference inside each byte plane. On ERA5 float32 data the median ratio across codecs was bytedelta 5.86x, bitshuffle 5.62x, shuffle 5.1x, no filter 3.86x. On the pressure dataset with zstd level 9, 5.0x vs 4.0x for bitshuffle (about 25%); with always-split, 5.7x vs 4.1x (37%). It lowered the ratio on the precipitation dataset. — [Blosc: Bytedelta](https://blosc.org/posts/bytedelta-enhance-compression-toolset/)
- Bytedelta helps most with zstd and higher zlib levels; LZ4 and BloscLZ do better with bitshuffle. Compression at zstd levels 6 and 9 can take up to 2x longer with bytedelta; decompression slows by up to 20% or more for most codecs, less for zstd. — [Blosc: Bytedelta](https://blosc.org/posts/bytedelta-enhance-compression-toolset/)
- Independent measurement on a 94.5 MB float32 test set: zstd alone 33.8 MB, Oodle Kraken 29.6 MB; "split bytes + delta" brings both to about 23 MB; float-level XOR after struct-of-arrays reorder gives about 28 MB; bitshuffle gave worse ratios than byte splitting; rotating the float by one bit to byte-align exponent and mantissa was "not an impressive result". — [Aras Pranckevicius, Float Compression 3: Filters](https://aras-p.info/blog/2023/02/01/Float-Compression-3-Filters/)
- Against that, FCBench finds bitshuffle+zstd the best overall of 13 methods on 33 datasets (1.466). FCBench did not include byte shuffle or bytedelta, so it does not settle bit vs byte. — [FCBench](https://arxiv.org/html/2312.10301v2)
- TDT reports a 1.24x geomean ratio improvement over bitshuffle+zstd from clustered byte grouping. — [TDT paper](https://arxiv.org/pdf/2506.18062v2)

Delta order selection and lookback (pco)
- pco's "Consecutive" delta takes differences of order o from 1 to 7, trying orders in sequence and stopping when estimated size grows; "Lookback" delta picks, per value, a lookback distance l and codes the value relative to the value l positions back, with the lookbacks stored as an extra latent stream; the paper describes this as capturing LZ-like repetition at number level instead of byte level. Selection is by compressing a sample of several runs of about 100 consecutive numbers. — [Pcodec paper](https://arxiv.org/html/2502.06112v2)

RLE, dictionary, frequency, cascades (BtrBlocks, FastLanes)
- BtrBlocks scheme pool: One Value, RLE, Dictionary, Frequency (most frequent value + bitmap + exceptions; excluded at 50% or more uniques), FOR + bit-packing with exceptions, FSST, Pseudodecimal, Roaring for NULLs. Selection samples 10 runs of 64 values per 64,000-value block (about 1%), costs about 1.2% of compression time, matches the optimal scheme about 77% of the time and is on average 3.3% worse than optimal; cascade depth is capped at 3; RLE is excluded when mean run length is below 2. — [BtrBlocks paper](https://www.cs.cit.tum.de:443/fileadmin/w00cfj/dis/papers/btrblocks.pdf)
- BtrBlocks ratio vs Parquet on Public BI / TPC-H: Parquet 3.37x / 1.69x; Parquet+Snappy 4.79x / 2.85x; Parquet+Zstd 6.05x / 3.41x; BtrBlocks 5.28x / 3.79x. In-memory decompression 3.8x (Public BI) and 4.2x (TPC-H) faster than Parquet+Zstd. — [BtrBlocks paper](https://www.cs.cit.tum.de:443/fileadmin/w00cfj/dis/papers/btrblocks.pdf)
- FastLanes file format ablation (ratio lost when an encoding is removed from the pool, Public BI): Dictionary +42.36%, DELTA +5.92%, FSST +3.86%. Frequency encoding was dropped because its gain was tiny (0.05% in the text, 0.09% in the table). CROSS_RLE runs RLE across a whole row group to avoid per-vector overhead; FRLE maps RLE onto dictionary + delta-coded indexes. — [The FastLanes File Format](https://ir.cwi.nl/pub/35881/35881.pdf)
- FastLanes expression choice: a rule phase (constant, equal columns, string-as-number, double-as-integer, narrower integer type, one-to-one map) then sampling the first, middle and last vectors, reported to reach over 99% of the best ratio. — [The FastLanes File Format](https://ir.cwi.nl/pub/35881/35881.pdf)
- FastLanes without any general-purpose compressor is 2.0% smaller than Parquet+Zstd on Public BI (and 18% smaller than BtrBlocks), but 15.3% larger than Parquet+Zstd on TPC-H; decoding is reported 44x faster than Parquet+Zstd. — [The FastLanes File Format](https://ir.cwi.nl/pub/35881/35881.pdf)

Linear / piecewise-linear models (LeCo, SIGMOD 2024)
- LeCo fits a regressor per partition (constant = FOR, linear, polynomial, exponential, logarithmic, sine terms) minimising the maximum error, and bit-packs fixed-width residuals; partitions are fixed-length or variable-length via greedy split-and-merge. — [LeCo](https://arxiv.org/pdf/2306.15374v3.pdf)
- Gain over FOR averages about 40.9% on locally smooth datasets and 9.3% on locally hard ones (headline up to 91% over FOR and Elias-Fano); variable-length partitioning adds about 28.2% on four datasets and under 10% elsewhere; higher-order models gave up to 64.7% over linear-only on data with such patterns. Against Delta the gains are large on smooth synthetic data and "competitive" on real data. — [LeCo](https://arxiv.org/pdf/2306.15374v3.pdf)
- Compression speed GB/s: FOR 0.81, Delta-fix 1.04, LeCo-fix 0.78, LeCo-var 0.02, Delta-var 0.04. Full decode for LeCo-fix is 14 to 34% slower than FOR. — [LeCo](https://arxiv.org/pdf/2306.15374v3.pdf)
- In Parquet, adding zstd on top gives LeCo a larger further gain than it gives FOR, i.e. the two are partly complementary. — [LeCo](https://arxiv.org/pdf/2306.15374v3.pdf)

Cross-column correlation (Corra, C3, FastLanes MCC, Virtual)
- Corra schemes: (1) diff-encode a column against a reference column; (2) hierarchical encoding for containment pairs (city then zip): per-parent child list plus offsets; (3) multi-reference: a 2-bit code selects which groups of reference columns sum to the target, with non-matching rows stored as outliers (row index + value). — [Corra](https://arxiv.org/html/2403.17229v2)
- Corra savings versus the best single-column encoding: l_receiptdate vs l_shipdate 58.3%; l_commitdate 33.3%; Taxi dropoff vs pickup 30.6%; DMV zip vs city 53.7%; DMV city vs state 1.8%; ip vs countryid 17.1%; Taxi total_amount from 8 reference columns 85.16% with about 0.32% outliers. Query slowdowns on the encoded column alone: up to 1.66x (diff), 1.39 to 1.56x (hierarchical), about 2x (multi-reference). — [Corra](https://arxiv.org/html/2403.17229v2)
- C3 schemes: Equality (source + exceptions), Numerical (target as delta from a linear function of source, bit-packed), 1-to-1 Dictionary, 1-to-N Dictionary, Dictionary-FOR / DFOR (subtract a per-source-value minimum from the target), Dictionary Sharing. Selection: statistics pruning within a 100-column window, sampled estimates, a correlation graph with greedy edge selection, and reversal if the real size is worse. Reported result: 1.2x higher compression ratio than single-column schemes alone on a Public BI subset. — [Glas, Exploiting Column Correlations for Compression (CWI MSc thesis)](https://homepages.cwi.nl/~boncz/msc/2023-ThomasGlas.pdf)
- Corra vs C3 on the same pairs: commitdate 33.3% vs 31.5%; receiptdate 58.3% vs 56.1%; dropoff 30.6% vs 52.9% (C3 models an affine relation); zip 53.7% vs 59.1%. — [Corra](https://arxiv.org/html/2403.17229v2)
- FastLanes multi-column gains on Public BI (compression / decode speed): Equality +4.70% / +2.66%; One-to-One map +1.17% / +9.47%; Cast (string-as-number etc.) +0.78% / +10.16%; summarised as roughly +8% compression and +20% decode speed. — [The FastLanes File Format](https://ir.cwi.nl/pub/35881/35881.pdf)
- "Virtual" (Stoian et al., 2024) is a further lightweight correlation-aware table compressor benchmarked against Parquet+Snappy and DeepSqueeze; it characterises C3 as applying only simple linear regression to numeric column pairs. — [Virtual: Lightweight Correlation-Aware Table Compression](https://arxiv.org/pdf/2410.14066)

Integer multiples and tokenising
- pco IntMult models x = q x m + r, splitting into a quotient stream and a remainder stream (unlike plain gcd division it tolerates a non-zero, noisy remainder, for example millisecond timestamps stored as microseconds with jitter); candidate m comes from gcds of sampled triples. — [Pcodec paper](https://arxiv.org/html/2502.06112v2)
- OpenZL ships Tokenize (unique tokens + index stream), Delta, Divide By, Range Pack, Merge Sorted, Quantize, Prefix, Dedup, Field LZ, Transpose, Zigzag, Bitpack, Flatpack, Constant, Parse Int, Split, Split By Struct, Float Deconstruct. — [OpenZL codec navigation](https://openzl.org/api/py/codecs/ace/)

### Inferences
- Ranked by expected value for kolmo given what it already has (my judgement, grounded in the numbers above):
  1. Cross-column nodes: diff against reference column (after delta or not), equality with exceptions, one-to-one map, per-key FOR (DFOR). Reported 1.2x table-level (C3), about 8% (FastLanes), and 30 to 58% on individual date/time columns. These are invisible to a per-stream entropy coder unless it is a context mixer with cross-column contexts, so the gain should survive zstd/BWT. Cost is mainly the pair search; C3 and FastLanes both bound it with rules plus sampling.
  2. Number-level lookback delta (pco) and "XOR/sub with previous row" for fixed records: an LZ stage after byte planes cannot find a repeated 8-byte value once its bytes are in different planes, so a value-level match stream is complementary to byte planes. No isolated ablation is published.
  3. Delta order chosen by trial up to order 7 (kolmo has orders 1 and 2). Cheap; gain only on smooth sampled signals.
  4. Bytedelta inside byte planes as an alternative to value-level delta: measured 5 to 37% over bitshuffle and about 15% over shuffle with zstd on some float32 grids, negative on others, so it must be chosen per stream. Trivial to implement (a SIMD subtract).
  5. IntMult with remainder stream as a generalisation of gcd division. Small but cheap, and it covers the case where gcd is 1 because of a handful of off-grid values.
  6. Linear / piecewise-linear residuals: LeCo's 9% on "hard" real data and 41% on smooth data is versus FOR, not versus delta; against delta the paper only claims parity on real data. Since kolmo has delta and delta2 (which already cancel a linear trend), expected extra gain is small except for random access. Low priority.
  7. Frequency encoding: FastLanes measured 0.05 to 0.09% and removed it. Skip, or keep only as "one dominant value + exceptions" if it falls out of an RLE/constant node for free.
- Bit vs byte planes: the evidence conflicts (FCBench favours bitshuffle+zstd among its candidates; Blosc and Aras measure shuffle+bytedelta ahead of bitshuffle; Blosc finds bitshuffle better for LZ4-class codecs). The practical reading is that bitshuffle is worth having as a selectable alternative for fast LZ leaves and noisy full-precision data, not as a replacement.
- Sampling budgets that the literature found sufficient: about 1% of a block in 10 runs of 64 (BtrBlocks, 3.3% from optimal) or three vectors (FastLanes, over 99% of best). Useful priors for kolmo's planner.

### Gaps
- Delta-of-delta specifically for timestamps, run-end encoding, sorted dictionaries, sort-and-permute columns, nibble-plane splitting, DeltaStride, seasonal/periodic predictors, TurboPFor block schemes, Data Blocks, CORBIT, and the Parquet/ORC/DuckDB encoding specs: I found no source this session with isolated size measurements for these when followed by zstd/BWT, and did not fetch their specs. They are standard and cheap, but any gain claim would be unsourced. (kolmo's existing delta2 is delta-of-delta.)
- pco's lookback delta has no published ablation; the paper gives only end-to-end numbers.
- The C3 thesis results chapter was truncated in the fetch; only the abstract-level 1.2x figure was obtained, with no decompression cost.
- Virtual's own compression numbers were not extracted.

## 3. What exactly does pcodec (pco) do, and what does it report?

### Takeaway
pco is "mode split, then delta, then binning with tANS for the bin index and raw offset bits within the bin"; its four modes are Classic, IntMult, FloatMult and FloatQuant, chosen per chunk from a small sample by estimated bit savings. It reports 29 to 94% better ratio than the best alternative (Blosc shuffle+zstd, Parquet+zstd, SPDP, TurboPFor+zstd) on six datasets at above 1 GiB/s decode, but publishes no comparison with ALP and no per-mode ablation.

### Cited Findings
- Pipeline: each chunk gets exactly one mode, which splits every number into one or two unsigned "latent" streams; each latent stream gets one delta encoding (None, Consecutive order 1 to 7, or Lookback); each stream is then binned and coded. — [Pcodec paper](https://arxiv.org/html/2502.06112v2)
- Classic: one latent, an order-preserving map to unsigned (for floats, flip the sign bit of positives and all bits of negatives so integer order equals numeric order). — [Pcodec paper](https://arxiv.org/html/2502.06112v2)
- IntMult: x = q x m + r with q = floor(x / m), r = x mod m; two latents (q and r). Candidate m from gcd(x2 - x1, x3 - x1) over sampled triples, favouring values that occur anomalously often; accepted when estimated quotient saving (about log2 m bits per number) exceeds a worst-case entropy bound on the remainder. — [Pcodec paper](https://arxiv.org/html/2502.06112v2)
- FloatMult: for floats that are mostly multiples of a base such as 0.01; the paper gives the example and says cost estimation is analogous to IntMult but does not spell out the formula. — [Pcodec paper](https://arxiv.org/html/2502.06112v2)
- FloatQuant: for floats whose low k mantissa bits are mostly zero (example: 16-bit floats stored as 32-bit). In the source, primary = ordered_bits >> k and secondary = the low k bits (complemented for negatives so exact values give zero); k is chosen from a histogram of trailing-zero counts in a sample, taking the first local maximum of "k minus worst-case bits for the non-zero secondaries"; the mode only bids if the average saving exceeds a required-bits threshold. Test cases in the source: integers 0..99 stored as f32 give k = 17; a sample of only 0.0 and 1.0 is rejected as too easy to memorise. — [pco float_quant.rs](https://docs.rs/crate/pco/latest/source/src/mode/float_quant.rs)
- Mode detection runs on a deterministic random sample of a few percent of the numbers; each non-Classic mode bids a parameter and an estimated saving, lowest estimated cost wins. — [Pcodec paper](https://arxiv.org/html/2502.06112v2)
- Binning: build a histogram of up to 256 tight bins (bounds are actual values), then an O(k^2) dynamic program merges adjacent bins to minimise metadata + count x (log2(total/count) + ceil(log2(range))). The bin index is coded with 4-way interleaved tANS and the offset inside the bin with a fixed number of raw bits; data is written in batches of 256 (256 tANS codes, then 256 offsets). — [Pcodec paper](https://arxiv.org/html/2502.06112v2)
- Ratio at default level versus the best alternative given up to 50% more compression time: Air Quality 14.62 vs 7.54 (Blosc shuffle+zstd), +94%; Housing 3.07 vs 2.37, +29%; Payments 12.21 vs 9.06 (zstd), +35%; r/place 6.30 vs 4.18, +51%; Taxi 6.94 vs 5.29 (Parquet dict+zstd), +31%; Twitter 18.04 vs 13.74 (SPDP), +31%. — [Pcodec paper](https://arxiv.org/html/2502.06112v2)
- Single-thread decompression MiB/s: pco 1,432 to 5,450 across the six datasets; Blosc2 shuffle+zstd 1,416 to 6,836; Parquet delta+zstd 1,679 to 4,910; TurboPFor+zstd 1,015 to 4,877; plain zstd 1,069 to 1,973; SPDP 287 to 539. Compression speed is given only as a plot. — [Pcodec paper](https://arxiv.org/html/2502.06112v2)
- Limits stated or evident: one mode and one delta per chunk; six datasets, capped at 2M rows; ALP, Chimp and FastLanes are not in the comparison; no ablation of modes or delta types; no separate study of full-precision floats. — [Pcodec paper](https://arxiv.org/html/2502.06112v2)

### Inferences
- The piece of pco most likely to be new to kolmo is the binning leaf: "entropy-code which range the value falls in, store the position within the range as raw bits". For wide integers with a smooth, non-byte-aligned distribution this avoids the loss byte planes incur when the informative bits straddle a byte boundary, and it is what lets pco beat shuffle+zstd by 29 to 94%. It is a leaf codec, not a transform, but it stacks under every existing kolmo transform (delta, FOR, decimal node output). kolmo dropped Rice and plain bit-packing; binning + ANS is the adaptive generalisation of both and may not have been measured. Cost: histogram + DP merge + tANS, roughly 500 to 800 lines of C if rANS/tANS already exists.
- FloatQuant overlaps kolmo's "mantissa truncation / trailing zero" idea; the detail worth copying is that it shifts on the order-preserving integer and keeps a (mostly zero) secondary stream instead of requiring all values to conform, so no exception list is needed.
- FloatMult overlaps the ALP-style decimal node but with an arbitrary base (not only powers of ten) and a tolerated remainder stream; it would cover "value = k x step" quantised floats such as 1/3-stop, 0.25 or sensor ADC steps. Exact FloatMult detection could not be sourced (format.md blocked).
- pco's headline gains are measured against byte-oriented pipelines, not against ALP+cascade or a context mixer, so they are an upper bound on what kolmo would see.

### Gaps
- pco format spec (`github.com/pcodec/pcodec/blob/main/docs/format.md`) could not be fetched; exact FloatMult formula, the Lookback selection method, and any newer modes or delta types added after the paper (the repository may have added more since early 2025) are unverified.
- No published pco vs ALP or pco vs OpenZL numbers were found.
- The required-bits threshold constant for FloatQuant was not visible.

## 4. What numeric nodes does OpenZL offer, and which matter most?

### Takeaway
OpenZL's numeric codec list is essentially the set kolmo already has plus Tokenize, Field LZ, Range Pack, Merge Sorted, Quantize, Prefix, Dedup, Divide By, Parse Int and Flatpack; the paper does not rank codecs, and attributes most of the gain to parsing into typed streams and to trained graph selection (ACE), not to any single transform.

### Cited Findings
- Codecs listed in the OpenZL Python API navigation: ACE, Bitpack, Bitunpack, Brute Force, Compress, Concat, Constant, Conversion, SDDL, Dedup, Delta, Dispatch, Divide By, Entropy, Field Lz, Flatpack, Float Deconstruct, Merge Sorted, Parse Int, Prefix, Quantize, Range Pack, Split By Struct, Split, Store, Tokenize, Transpose, Zigzag, Zstd. — [openzl.org codecs](https://openzl.org/api/py/codecs/ace/)
- Paper descriptions: Tokenize outputs unique tokens (alphabet) plus an index stream and "works best as an intermediate step"; Field LZ runs LZ over fixed-width struct streams and matches whole structs, not bytes; Delta is applied to sorted integers; Parse Int converts ASCII integers to binary; Dispatch routes bytes into typed output streams; FSE and Huffman are the entropy back-ends; ACE (Automatic Compression Explorer) uses a genetic algorithm to build back-end graphs; a clustering graph groups similar streams. Divide By, Float Deconstruct, Prefix, Range Pack, Transpose, Zigzag, Split, Constant and Bitpack are named but not described. — [OpenZL paper](https://arxiv.org/pdf/2510.03203)
- Ratios, OpenZL / xz -9 / zstd -19: ppmf_person 116.70 / 69.10 / 60.15; psam_p 8.59 / 6.75 / 6.47; binance_canonical 3.01 / 2.62 / 2.15; tlc_canonical 11.42 / 10.52 / 8.95; rea6_precip 24.82 / 21.44 / 18.07; era5_flux 13.62 / 8.73 / 7.45; era5_precip 13.00 / 11.19 / 9.49; era5_pressure 11.20 / 6.58 / 5.60; era5_snow 58.25 / 47.76 / 41.01; era5_wind 6.82 / 4.88 / 4.12. — [OpenZL paper](https://arxiv.org/pdf/2510.03203)
- Blosc on the same ERA5/REA6 sets: 16.21 (rea6), 7.96 (flux), 7.86 (precip), 6.01 (pressure), 33.97 (snow), 4.17 (wind); OpenZL is ahead on all. — [OpenZL paper](https://arxiv.org/pdf/2510.03203)
- Speeds MiB/s, OpenZL compress / decompress: era5_pressure 417 / 873; era5_flux 268 / 1450; rea6_precip 237 / 2140; tlc 197 / 1180; binance 53.7 / 703; psam_p 23.8 / 49.4; ppmf_person 68.4 / 147. zstd -19 compresses at about 1 to 20 MiB/s on the same data. — [OpenZL paper](https://arxiv.org/pdf/2510.03203)
- The paper states that parsing "usually represents the bulk of the work", that transform choice can make compression "both faster and stronger", and that training is its most effective tool; it gives no per-codec ablation. On enwik7 OpenZL reaches 3.04 versus 3.68 (xz) and 3.58 (zstd -19), attributed to lacking text codecs. — [OpenZL paper](https://arxiv.org/pdf/2510.03203)

### Inferences
- Candidate nodes kolmo may lack, in my order of likely value: Field LZ (struct-granular LZ: match offsets and lengths in units of the element width, with literals handed on as a typed numeric stream; it is the same idea as pco's lookback and should help repeated-but-unsorted numeric columns), Tokenize with a sorted alphabet followed by delta on the alphabet (low-cardinality wide values), Range Pack (subtract min then narrow to the smallest integer width, i.e. width narrowing instead of bit-packing, which keeps streams byte-aligned for the entropy leaf), Merge Sorted (several sorted runs merged into one sorted stream plus a small source-index stream, for concatenated sorted chunks), Dedup (identical streams stored once, the stream-level analogue of FastLanes Equality), Prefix (shared prefix lengths for sorted strings).
- The era5_pressure result (11.20 vs Blosc 6.01 vs zstd 5.60) is on gridded float32 that Blosc's shuffle + bytedelta family targets, so graph selection plus numeric nodes roughly doubled the shuffle+LZ result there; this is the kind of data where the "full-precision" techniques in question 5 pay.

### Gaps
- Exact semantics of Quantize, Merge Sorted, Range Pack, Prefix, Flatpack, Divide By and Float Deconstruct are inferred from names and prior knowledge; the per-codec doc pages were not fetched, and the paper does not describe them. In particular whether OpenZL's Quantize is a lossless bucket + offset split (like pco binning) is unverified.
- No public statement was found ranking OpenZL codecs by contribution, and no OpenZL release notes after v0.3.0 were read, so newer numeric nodes may exist.

## 5. Which techniques help genuinely full-precision float64 (scientific, image-derived)?

### Takeaway
Expect about 1.1x to 1.5x at best: the benchmark median for doubles is about 1.2x, and the methods that reach the top are plane transposition (bit or byte) with an LZ/entropy back-end, Lorenzo-style n-D prediction (fpzip, about 1.6x on HPC data but at under 0.1 GB/s), byte-delta inside planes for smooth grids, and data-driven grouping of byte planes; decimal schemes and XOR schemes add nothing here.

### Cited Findings
- FCBench medians: 1.202 for double precision, 1.225 for single; HPC domain median 1.206; best HPC method fpzip at 1.601 average, then bitshuffle+zstd 1.468, ndzip-CPU 1.450, bitshuffle+LZ4 1.447, MPC 1.399, SPDP 1.381, Chimp 1.232, pFPC 1.229, Gorilla 1.161. — [FCBench](https://arxiv.org/html/2312.10301v2)
- fpzip's HPC lead costs speed: 0.079 GB/s compress and 0.074 GB/s decompress versus 1.407 / 1.328 for bitshuffle+zstd and 2.192 / 1.636 for ndzip-CPU. — [FCBench](https://arxiv.org/html/2312.10301v2)
- Dimensionality information did not significantly change ratio for the predictors tested (fpzip 1.334 multi-dimensional vs 1.326 as 1-D). — [FCBench](https://arxiv.org/html/2312.10301v2)
- ALP-RD on high-precision coordinates: 55.5 and 56.4 bits/value (about 1.15x), losing to zstd at 48.1 and 53.1; the paper caps ALP-RD at about 1.2x. PDE gets 1.0x on the high-precision NYC/29 column. — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf); [BtrBlocks paper](https://www.cs.cit.tum.de:443/fileadmin/w00cfj/dis/papers/btrblocks.pdf)
- float32 model weights: ALP-RD32 28.1 bits vs zstd 29.7 (about 5% better than zstd, 12% below raw). — [ALP paper, CWI](https://ir.cwi.nl/pub/33334/33334.pdf)
- TDT on float64 scientific sets with zstd: num-brain 1.265 vs 1.065; astro-pt 1.366 vs 1.047; msg-bt 1.383 vs 1.126; num-control 1.146 vs 1.058 (zstd alone is near 1.05 on these); float64 geomean improvement 1.075x. — [TDT paper](https://arxiv.org/pdf/2506.18062v2)
- Byte-delta within planes on smooth float32 grids: up to 37% over bitshuffle with zstd on ERA5 pressure, negative on precipitation. — [Blosc: Bytedelta](https://blosc.org/posts/bytedelta-enhance-compression-toolset/)
- Float-level XOR or integer delta after struct-of-arrays reorder helped zstd and LZ4 substantially on one float32 simulation/image-like set (33.8 MB to about 28 MB), and byte split + byte delta did better still (about 23 MB). — [Aras Pranckevicius, Float Compression 3](https://aras-p.info/blog/2023/02/01/Float-Compression-3-Filters/)
- pco FloatQuant targets floats with unused low mantissa bits (e.g. narrower floats widened), and Classic mode's order-preserving integer map lets delta and binning work on full-precision floats as ordered integers. — [pco float_quant.rs](https://docs.rs/crate/pco/latest/source/src/mode/float_quant.rs); [Pcodec paper](https://arxiv.org/html/2502.06112v2)

### Inferences
- For full-precision float64 the low 3 to 5 mantissa bytes are close to incompressible; the achievable gain is concentrated in sign, exponent and the top 1 to 3 mantissa bytes. Concretely for kolmo:
  1. Do integer delta (or Lorenzo/gradient prediction for 2-D and 3-D grids) on the order-preserving integer image of the float, then split planes. kolmo's 8-bit gradient predictor could be generalised to 16/32/64-bit ordered-integer samples; this is the fpzip idea without its slow range coder, and FCBench shows the Lorenzo family leads on HPC data. The FCBench "dimensions do not matter" result argues that 1-D delta captures most of it, so the n-D version is a small-gain item.
  2. Store the noisy low planes raw (or with the cheapest leaf) and spend modelling only on the top planes; choose the plane grouping by entropy as in TDT (reported 7.5% geomean on float64, 20 to 30% on some scientific sets versus plain zstd, though against a plain non-shuffled baseline, so the increment over kolmo's existing planes will be smaller).
  3. Offer bytedelta inside the top planes as an alternative to value delta, selected per stream.
  4. Detect disguised narrower types first: float32 widened to float64, integers stored as floats, fixed trailing-zero count (FloatQuant), value = k x step (FloatMult). These convert "full-precision-looking" columns into easy ones and are the only route to large gains.
- Everything above is consistent with a realistic ceiling of roughly 1.2x to 1.6x on true scientific doubles; claims well beyond that in papers come from decimal-origin or low-entropy columns.

### Gaps
- No source measured ordered-integer delta + plane split + zstd/BWT against fpzip or bitshuffle+zstd on the same float64 data; the ranking of item 1 above against bitshuffle+zstd is unverified.
- No lossless results for image-derived float64 specifically (e.g. reprojected satellite rasters) were found.
- zfp's lossless mode, MPC, and ndzip details were not fetched; FCBench numbers are the only data here for them.
- FCBench did not test byte shuffle, bytedelta, ALP, pco or Elf, so there is no single benchmark that ranks all the candidates on full-precision data.
