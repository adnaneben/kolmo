# Wire review, 13 November 2026 (user-approved item 2)

Scope:
- **(A)** Singleton `C_RANS` chunks, as emitted by the research encoders `tp_prans`, `tp_pent` and `tp_arch19`.
- **(B)** The proposed fast order-1 entropy leaf for value-Markov series such as GHCN (PROVISIONAL P2-19).

This is a review only. No change to `src/`, `tests/`, `vendor/` or the format is made or authorized here.

## (A) Singleton `C_RANS` chunks: verdict CONFORMANT (an existing format, read by the existing decoder)

**What is emitted.** A `C_RANS` leaf is a sequence of chunks. Each chunk is:
- the raw length as a uv;
- a frequency table: per symbol a uv frequency, with a 0 followed by a run count for absent symbols;
- the coded length as a uv;
- the coded bytes: four 64-bit states, then renormalisation words.

The research encoder (`P2-E13/rans1.inc`, generated by `gen_rans1.py` from the pinned core blob `e06467c…`) differs
from production in one line. A chunk with one distinct symbol gets frequency `RANS_M = 65536` instead of being
refused. Chunks are aligned to residual byte planes, and the decoder already accepts any chunk length up to 1 MiB.

**Decoder trace** (`rans_decompress_all`, `src/kolmo.c`, unchanged since C_RANS was introduced; only the
`czn→kolmo` rename touched it):

| Step | Check | Singleton chunk |
|---|---|---|
| Table | each `v ≤ RANS_M`; cumulative `c[256] == RANS_M` | `f[s] = 65536`, others 0 → `c[256] = 65536` ✓ |
| Coded length | `z ≥ 32`, `z % 4 == 0`, `z ≤ remaining` | encoder emits exactly 32 bytes (4 states, no words) ✓ |
| States | each `x ≥ R64_L` | encoder states stay at `R64_L` ✓ |
| Decode step | `X = f[k]·(X >> 16) + slot − c[k]` | `= 65536·(X >> 16) + (X & 0xFFFF) = X`; no renormalisation ✓ |
| End | `p == pe` and every state is back at `R64_L` | ✓ |

Encoder side: `r64sym_init(f = 65536)` gives `cmpl = 0` and `xmax = 2^63`, so `X` never changes and nothing is output.

**Evidence:**
- R1 review: 272 single-symbol cases decoded with the pinned decoder.
- P2-E13: 60/60 corpus frames, and 360/360 random NPY arrays including constant and two-symbol arrays, with an
  ASan/UBSan/LSan encoder.
- P2-E14, P2-E17 and the pending P2-E20: every `tp_pent`/`tp_arch19` frame was decoded by the production CLI inside
  sanitizer gates (427/427 and 183/183).
- This review: a **mutation fuzz of singleton-heavy frames against an ASan/UBSan build of the unmodified production
  decoder CLI**. That was 3 × 1,500 mutants (1–8 byte mutations) with **0 sanitizer findings**. 1,466 per frame were
  rejected cleanly; 11–12 decoded, meaning they passed the block checksum, as when an unused byte is changed.
  Results are in `evidence/fuzz_summary.txt`, with the harness in `evidence/fuzz.py` and frame hashes in
  `evidence/frames.sha256`.

**Caveats:**
1. A singleton chunk costs its table (about 3–5 bytes) plus 32 bytes of state. Huffman's repeated-byte mode is smaller,
   so an encoder should prefer `C_HUF` or a stored leaf when a whole leaf is near-singleton. `tp_pent` already chooses
   the smaller of the whole-leaf Huffman and rANS forms.
2. Decoders older than frame version 7 reject these frames, as they reject all graph frames. That is not new.
3. Side finding, not caused by this change: the production **CLI** (`src/cli.c:188/194`) does not free its input and
   output buffers before exit, so LeakSanitizer reports two direct leaks per `kolmo -d` run. The library decoder
   (`kolmo_decompress`) is leak-clean in-process (P2-E13 `mem` gates). Reported only; `src/` is frozen here.

**Recommendation.** Research encoders may keep emitting singleton `C_RANS` chunks: this is conformant use of the
existing wire format, with no new semantics or ID. For a production encoder to emit them, two changes would be
needed, each needing its own authorization:
- the one-line `rans_norm` change in `src/`;
- conformance vectors (singleton, plane-aligned and 1 MiB-boundary chunks) added to `tests/`.

## (B) Fast order-1 entropy leaf (proposal P2-19): verdict NEW WIRE SEMANTICS, design recorded, not implemented

**Why.** P2-E18 found that GHCN series have H(x | previous x) 15–20% below the order-0 entropy. The production
leaves either do not use that context (Huffman, rANS, zstd) or are far too slow under P2's archive cost (CM about
15–25× over; BSC +5–16%, local measurement).

**Proposed codec ID 15, `C_RANS1`.** This is a new ID. ID 14 must never be reused for a different inverse.
- Chunked like `C_RANS`. Each chunk carries:
  - the raw length (uv);
  - `K` contexts (uv, 1 ≤ K ≤ 32);
  - a 256-entry context map from the previous byte to a context, run-length coded;
  - `K` frequency tables in `C_RANS`'s table syntax at 12-bit precision (`M = 4096`), which keeps each slot table
    at 4 KiB and the total at ≤ 128 KiB;
  - the coded length;
  - the states (`C_RANS`'s 4-way interleave), with context taken from the previous decoded byte *of the same
    interleave lane* so the four lanes stay independent.
- First byte context = 0. A chunk boundary resets the context.
- Old decoders fail cleanly: `codec_decompress` returns −1 for an unknown codec (checked in this review), and graph
  leaves use that path.
- Limits to enforce in the decoder: `K ≤ 32`; every table sums to `M`; `z ≥ 32` and `z % 4 == 0`; each chunk's raw
  length ≤ 1 MiB; final states equal `L`.

**Open questions before implementation:**
- Whether lane-local context loses too much: an alternative is a 2-way interleave with global context.
- The table cost on small chunks.
- Whether value-level context (16-bit offsets) needs the context from the high plane rather than the previous byte.

**Next step.** Build a research-container prototype, not a production frame, to measure bytes and decode speed on
the GHCN development inputs against OpenZL-9's cost. A production implementation and a decoder change in `src/`
would need explicit authorization and a separate review of the frozen design.

### (B) addendum: feasibility estimate before any prototype (same day)

I computed ideal code lengths on the nine GHCN development inputs (`evidence/order1_estimate.py` and `.txt`; the
input hashes are in `P2-E18/results/ghcn.sha256`).

**Static tables cost too much.** Static order-1 tables at a realistic cost (about 1.5 bytes per used symbol per
context) add 10–20% to the output. With them, static order-1 is *larger* than OpenZL-9 on every temperature series.
The `C_RANS1` design above therefore does not reach its goal as written.

**An adaptive order-1 model only reaches parity.** It needs no tables (ideal code length, value | previous value):

| Series | Adaptive order-1 vs OpenZL-9 |
|---|---|
| TMAX / TMIN | 23,983 vs 26,169; 21,125 vs 21,937; 16,224 vs 15,836; 13,472 vs 13,451; 38,737 vs 38,645; 35,139 vs 37,357 |
| Range | −8% to +2.5% |

That is before any decoder-speed cost. Plain adaptive *order-0* values beat OpenZL on PRCP by 2–14%, but per-plane
rANS (`tp_pent`) is already close there.

**Revised recommendation: do not pursue P2-19 now.** The best case is roughly OpenZL-9 parity on GHCN, while the
decoder would need to run at OpenZL's speed. Only the much slower CM model clearly beats it. A new codec ID is not
justified by this evidence. PROVISIONAL P2-19 is downgraded accordingly.
