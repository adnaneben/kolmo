## Timing boundary

One process links all arms. Original bytes are loaded once outside timers. Every timed encoding starts from the SAME full original bytes; typing, the original predictor/GCD path, allocations, internal probes and rejected leaf trials, framing, content checksums and cleanup are charged. No precomputed residuals or candidate selection are free. All OpenZL contexts and its graph are rebuilt in each encode, as the frozen adapter specifies. Production Kolmo includes its original planner; this is a diagnostic baseline, not a column-first candidate.

Independent warm encoding and decoding rounds; deterministic randomized arm order. First pass 7 rounds, confirmation 5. Batch count `max(1,min(16,floor(4 MiB/input_bytes)))` is fixed by input length and identical across arms. Each batch retains its outputs until validation, verifies EVERY output byte outside the timer, and separately times destruction; allocation and destruction time are both included. Retaining a bounded batch can affect allocation/cache history, so this is a declared batched API boundary, not a guarantee for an application allocating one message at a time. The small pending-object vector is reserved outside timing, equally for all arms. No disk I/O, process startup, Python launch or final output-file write is timed for ANY arm. Do not pool these timings with prior CLI or residual-only studies.

Frame/content integrity behavior stays at the frozen codec defaults: zstd3 is the existing checksum-off P2 reference; Kolmo and OpenZL carry their existing integrity checks. External byte verification is mandatory for every arm. This is not an equal-integrity-feature API comparison; retain the difference in results and do not market a speed ratio as equal-feature dominance. No current codec/checksum setting may be silently changed during the study.

Record process CPU and wall time, then apply the existing >3% helper-thread CPU charging rule. This is warm timing only; cold/storage/cache-displaced regimes are NOT tested. No total-memory or scratch-memory claim follows from the process holding all gold frames.

## Correctness and execution

Gold frames are deterministically re-encoded and decoded exactly before timing. Every timed output is checked against the gold or original. All duplicate arms must yield identical frame bytes. All eight inputs, every configuration and both passes remain in the result; a failed arm invalidates this fixed matrix rather than disappearing from the denominator. Two-pass frame identities must agree. The Python ledger validator rejects missing, duplicate, malformed, nonfinite or inconsistent samples.

Infrastructure tests use explicitly labelled COPY-CODEC fixtures to exercise the C/C++ bridge, native timing loop, cleanup and failure checks. They are NOT compression benchmarks or tests of the upstream codecs. A real build and measurement remain separate gates. Previously passed upstream sanitizer counts are not reused as new passes.
