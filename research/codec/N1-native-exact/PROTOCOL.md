13 November 2026. This experiment addresses the recorded N1/P2-E17 comparison gap, not another codec claim. Source pin: OpenZL v0.3.0, 32246b48faee46807f84183dac4db479089f5445. All eight R3 prepared NPY inputs are previously observed; no fresh validation is claimed. No production source, other branch, mode/default or historical verdict may change. PR #7 remains draft.

## Frozen boundary
The native C++ encoder parses fixed-width integer NPY v1/v2/v3 or PCM16 RIFF/WAV headers before constructing a graph. Original header, payload and trailing bytes remain in original order. Typed payload is sent to OpenZL's official ACE-default NUMERIC graph after endian interpretation; original prefix/tail use ACE-default LZ. Standard SplitN and conversion nodes serialize all reconstruction information in an ordinary single-output OpenZL frame. The decoder needs no application parser or custom codec. Unknown, malformed, oversized or ambiguous types explicitly reject; there is no silent semantic conversion.

Levels 6 and 9; no training or custom graph tuning. Checksum options explicitly enabled. Compare exact header/payload splitting, the older whole-file-numeric interpretation (diagnostic), and whole-file serial LZ. All three use the same native process, pinned library and common compiler flags. Inputs are limited to 16 MiB, below the reference CLI's large-file segmenter scope; nested segmenters are illegal, so successor graphs use the official ACE defaults without a segmenter. This is a custom typed OpenZL encoder front end, not the unmodified OpenZL CLI or its global best achievable graph. Headers are compressed, not left uncounted or implicitly shared.

The NPY parser accepts only explicit byte order and signed/unsigned integer widths 1/2/4/8, shapes up to 32 dimensions, bounded lengths and a narrow Python-literal grammar. Original lexical bytes remain untouched. Nonempty WAV payloads are PCM16 with validated format/chunk sizes, frame alignment and a single data chunk. RIFF padding, extra chunks and trailing bytes are preserved. Exact parsing failure is an applicability result, not a false successful typed run.
